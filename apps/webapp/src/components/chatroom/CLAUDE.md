## Chatroom And Messaging

### Optimistic Message Lifecycle

- Client generates a UUID v4 via `crypto.randomUUID()` in `utils/clientMessageId.ts` and carries it from optimistic insert through Postgres INSERT to realtime echo. The same ID is reconciled in place; there is no remove + re-add.
- Do not reintroduce the literal `'fake_id'` placeholder. Two rapid sends collide in the store map and corrupt the optimistic UI.
- `MessageStatus = 'pending' | 'sent' | 'failed'` lives in `types/message.ts`. Server-fetched rows omit the field and are treated as `sent` (`status === 'sent' || !status`). No runtime `MESSAGE_STATUS` const; the literal type alone gives compile-time safety.
- `useReadCursor.advance` skips rows where `status !== 'sent'`; pending/failed optimistic rows must not advance the read cursor. The hook is monotonic (greatest()-on-server) and 1s-debounced, so callers can fire on every scroll tick.
- **Read-cursor advance is viewport-driven, not at-bottom-only.** `ChatList.onScroll` calls `advance(seq)` for the last fully-visible message on every scroll tick; `useChannelMessages.onInitialVisible` fires one rAF-polled seed after `data.replace` settles. Reducing this to an at-bottom-only signal regresses the Telegram-style UX (messages read while scrolling up never clear).
- **`advance_read_cursor` recomputes `unread_message_count`** in the same UPDATE that bumps `last_read_seq` (plus stamps `last_read_update_at`); without the recompute the TOC badge desyncs forever. The TOC `<UnreadBadge>` and `<JumpToPresentButton>` both read `useUnreadCount(channelId)` (not raw `channels.*.unread_message_count` alone). `useUnreadCount` prefers `optimisticUnreadStore` while the user is reading in-view. `ChatroomContext` decrements on viewport cursor advance, and `useCatchUserPresences` reconciles via `setOptimisticUnread` on `channel_members` postgres_changes. Clear the map entry when the server count lands. `JumpToPresentButton` renders `max(unreadCount, newCount)` so persisted unread and session-local arrivals stack onto one chip.
- **`lastOptimisticSeqRef` MUST seed from `channel_members.last_read_seq`** once `isChannelDataLoaded` flips true. The ref tracks "highest seq the user has visually crossed in this session". If it starts at `0`, the first `onLastVisibleIndexChange` walk-backward counts every loaded message as newly crossed and decrements `optimisticUnread` by the entire window. Opening a chatroom with many unread then instantly zeros the badge. Seed from the persisted server cursor (`useChatStore.channelMembers.get(channelId).get(userId).last_read_seq`) so the walk only counts messages past the cursor (actual unread). Guard the seed with `if (lastOptimisticSeqRef.current > 0) return` so a later effect re-run doesn't undo session progress. Also: the store is named `optimisticUnreadStore` — never reintroduce `optical*` spellings.
- Send path: composer routes through `ChatroomContext.send` → `useSendMessage.send`. That call appends a `pending` row to Virtuoso's `data` and INSERTs directly via `persistChatMessage()` in `sendChatMessage.ts` (no `sendMessage` API on first send). On error, flips to `failed`; the postgres_changes INSERT echo flips it to `sent` via `useChannelRealtime`'s in-place merge. **Media sends:** `validate_message_medias()` requires each path to exist in `storage.objects` before INSERT/UPDATE — upload-then-send is load-bearing. Gate with `composerSendGate` / `isUploading` in the composer; confirm storage with `ensureChatMediaInsertReady()` in `chatMediaStorageReadiness.ts`. Every composer mode probes through `ensureOutboundStorageReady()` in `outboundMessagePipeline.ts` before it dispatches or clears. The early clear is the `cleanupAfterSubmit()` call that runs before dispatch when `shouldClearComposerEarly` is true. That holds when the send has no `htmlChunks` and is not an edit. A composer send sets `storageVerified`, so `persistChatMessage` skips its own probe. `retryChatMessage` still probes.
- **Own-send always scrolls to tail.** `data.append([optimistic], () => 'smooth')` is unconditional — the user follows their own message down even when scrolled up to re-read history. The `atBottom`-gated "don't yank" rule applies ONLY to others' arrivals in `useChannelRealtime`. Reverting to `({ atBottom }) => atBottom ? 'smooth' : false` here regresses Discord/Slack/Telegram parity for own sends.
- Duplicate-key classification is centralized in `components/chatroom/utils/postgresErrors.ts::isDuplicateKeyError`. Both `persistChatMessage` and `retryChatMessage` import it; do not inline PgError code/message checks.
- Retry path: failed-row tap → `ChatroomContext.retry(clientId)` → `useSendMessage.retry` → `retryChatMessage()` in `sendChatMessage.ts` (the only remaining caller of the `sendMessage` API). Re-issues with the original client UUID; 23505 duplicate-key is treated as success (the row was already persisted on a prior attempt). Returns `PersistChatMessageResult`; the caller (`useSendMessage.retry`) owns the pending/sent/failed UI flip against Virtuoso's data.
- **Sent attachments leave the strip with their uploads kept.** Every send with files calls `releaseSentAttachments` on the active list before its first await, the storage probe. A reply, comment or edit that ends during the probe or the send then finds none of the sent files to delete. A failed probe puts them back, and so does a failed edit. Only an edit calls `clearAttachments`, after it succeeds. A message split into chunks never carries files: `prepareOutboundContent` refuses files on a message over 3,000 characters. `cleanupAfterSubmit()` resets the reply or comment memory and clears the editor. The reset is a leave edge in the mode-edge table (§MessageComposer), so it deletes the upload of every entry that the mode added. The clear also fires the text writer in `useTiptapEditor`, which saves the draft list as the saved draft. A sent file left in the list would come back as a draft tile, and a second Send would post its upload twice. A failed row keeps the media for Retry and Delete. A send that fails with no row puts its attachments back when the editor is still empty and no mode is set. A failed comment has no row, so its text and comment mode go back too. The files that the comment added are recorded again, so a later cancel deletes their uploads.

### Message Grouping Projection

- Grouping flags are computed render-time in `ChatList/ItemContent.tsx::samePrev` against Virtuoso's `prevData`; never persisted, never written into `api/messages/*` types.
- Do not reintroduce a projection utility (`utils/projectMessageGroups.ts` and `utils/groupMessages.ts` are both gone) or an in-store mutation that writes grouping flags back onto rows. Out-of-order realtime arrivals and pagination merges corrupt flags whenever they're materialised.
- **Notification rows break grouping.** `ItemContent.tsx::samePrev` excludes `prevData.row.type === 'notification'` — without that exclusion, a notification chip between two same-author messages renders the post-notification message in `compact` mode (no avatar/header). The chip itself is `ChatList/SystemNotifyChip.tsx`, dispatched on `data.row.type === 'notification'`; `metadata.type` branches `user_join_workspace` / `title_changed` / `channel_created` / `user_join_channel` (last one returns null — the workspace-join chip already records first appearance).
- Virtuoso's `data` store is the single source of truth for in-view message rows; there is no parallel Zustand `channelMessagesStore`. Derive the newest seq from `useChannelMessages.newestSeqRef`; do not re-walk the list to compute it on hot paths.
- `MessageCardContext` must memoize its context value object (`useMemo`). A fresh object identity on every parent render cascades re-renders through every `MessageCard`.
- `MessageFooter` self-hides on `status === 'failed'`. Consumers (`DesktopEditor`, `ChatContainerMobile`) render `MessageCard.FailedRow` for owner rows and must not re-gate on `status`.
- **Desktop author-group left edge:** `DesktopMessageBody` always renders a fixed `w-10 shrink-0` leading rail beside a shared `flex-1` content column. The rail shows the avatar on group-start and the hover timestamp on compact. Compact rows must not drop the rail. Mobile non-owner compact rows keep a `size-10` spacer (`MobileMessageBody`). Every desktop card is full-width/cohesive (`w-full px-3` + hover/bookmark); media tiles self-cap via `CHAT_MEDIA_MAX_WIDTH_CLASS` — do not reintroduce the bespoke media-only card (`w-fit max-w-[min(400px,90%)] px-0 hover:bg-transparent`). Chat-bubble grouping is mobile-only.

### Chatroom List (Virtuoso)

- **`ItemLocation` is index-based.** `VirtuosoMessageList`'s `data.replace` and `scrollToItem` accept `{ index: number | 'LAST', align, behavior }`; the string `'lastItem'` and id-based `{ id, … }` shapes silently no-op behind the EmptyPlaceholder. Resolve a numeric index from the items array via `findIndex`; never wallpaper the call with `as any`.
- **A purge replace lands late.** On a list that already has rows, `data.replace(items, { purgeItemSizes: true })` parks the new rows until Virtuoso renders an empty list and waits one frame. An append in that gap goes into the old window, and the landing then drops it. That is how a send made far from the tail lost its optimistic row, and with it the text of a send that later failed. `useJumpTo` therefore waits until its window has landed, so await it before any append. `whenReplaced` checks for the first new item object; a 30-frame cap stops a hang when the list never renders. `whenReplaced` and the Virtuoso landing both run on animation frames, and a hidden tab runs none. So a send made far from the tail waits until the tab is shown again. Gaps are still open, because a replace keeps only the rows it is given. A send during the first window load, or during another send's jump, loses its row to the later replace. A realtime row drained after `applyWindowSeqRefs` and before the landing is lost too.
- **Layout contract.** `.message-feed` is `flex min-h-0 flex-1 flex-col overflow-hidden`; Virtuoso owns the scroll, not the wrapper. `<VirtuosoMessageList style={{ height: '100%' }}>` so the scroller fills the parent. Reverting `.message-feed` to a plain block + `overflow-y-auto` re-introduces an ~9000 px scroller stretch with items rendered far below the visible panel.
- **Panel resize bypasses React during drag.** During a drag, `useResizeContainer` writes `containerRef.current.style.height` and dispatches `CustomEvent('chat-panel-resize-tick', { detail: height })`. Per-mousemove Zustand writes cascade through every `state.chatRoom` subscriber → Virtuoso ResizeObserver → `bottom-smooth` thrash at 60Hz; direct-DOM avoids that. Each drag writes the store at most once (`setOrUpdateChatPanelHeight`), at release or when a settle ends. `stepChatRelease` is the only release step. Settle finish reads `mode`. Cleanup removes the listener and timer; it does not call `finish()`. Before a settle sets the to-height, one rAF passes, so React owns the from-height. Do not write 0 into `panelHeight` or `docsy:chat-height`. Reduced motion jumps. Its `abort-now` writes 320 to `style.height` itself, because React skips a `paint` that is already 320. A drag starts from `offsetHeight`, which counts the 1px `border-t`; `clientHeight` loses 1px on every click. Desktop only — do not change the mobile pane grabber. The snap recipe lives in [apps/webapp/CLAUDE.md](../../../CLAUDE.md) §Pad Workspace Surfaces; `useSyncChatPanelHeight` and the dead `marginBottom` live in its §Mobile Chat Pane.
- **Sticky day chip uses `getBoundingClientRect`, not `offsetTop`.** `StickyDayHeader` reads the topmost visible `[data-msg-date]` element via rAF-throttled `querySelectorAll` against the scroller. Virtuoso positions each item `absolute` inside a per-item wrapper, so `node.offsetTop` is 0 relative to that wrapper. The topmost-detection loop would therefore always return the first item regardless of scroll. Visibility is scroll-driven with a `HIDE_AFTER_MS = 1500` idle fade — `data-msg-date` is stamped on the message card outer div + inline `DateChip` + `SystemNotifyChip` wrappers.
- **Hover-menu integration (Floating UI + Virtuoso).** The four pieces are coupled and easy to misdiagnose individually — keep all of them in mind when any one breaks:
  1. **Visibility tracking → `IntersectionObserver`, not `getBoundingClientRect` polling.** Virtuoso items mount with transient/zero rects. A one-shot mount-time rect check sticks at `false`, which gates `useHover.enabled`. That gate silently disables the menu until the user scrolls. Bookmarked rows that mutate after mount (BookmarkIndicator + reactions render late) have the same failure mode without the scroll workaround. IntersectionObserver fires on initial paint _and_ on layout-driven intersection changes; both bugs collapse into one fix. Use `threshold: [0, 0.5, 1]` (not just `0.5`) so the first callback fires regardless of starting ratio.
  2. **`boundary` on `flip`/`shift` → `.message-feed`, not `.group/chat`.** The boundary defines the rectangle the floating menu cannot physically extend past. The panel-wide rect includes the toolbar and composer; a menu sitting _over_ the toolbar still fits inside the panel and won't trigger flip. `.message-feed` excludes both — top-of-feed messages flip to `bottom-end`. `position: fixed` can't be constrained by z-index or `overflow: hidden`; this is the only thing that actually keeps the menu inside the visual feed.
  3. **Portal target → `<div id="chat-hover-portal">` inside `ChatroomPanelLayout`.** Default `FloatingPortal` mounts at body root, which puts the menu in the root stacking context where nothing inside the panel can compete. Portaling inside the panel lets `JumpToPresentButton` (`z-40`) sit above the menu (`menuClassName="z-30"`) when both occupy the bottom-right region.
  4. **`safePolygon({ buffer: 8 })` + `delay.open: 100ms`.** `buffer: 1` required pixel-precise mouse paths from message → menu and felt broken; the user-visible complaint is "I have to exact-focus the message." 8px is the Floating UI example range. 100ms open beats 200ms perceptually without admitting accidental hovers.
- **Every message menu renders `MessageActionMenuList`: right-click, hover ⋯ (through `MessageContextMenu/ContextMenuItems.tsx`) and long press.** Rows and titles come from `useMessageActionMenuItems.tsx`, a subset uses the `only` prop, and confirms open through `GlobalDialog`, because `ChatroomContext` has no dialog host. The hover ⋯ lists shared rows in the right-click order: Copy link, Download, Copy to doc, Edit, Delete. Every menu draws 16px icons (`MESSAGE_MENU_ICON_SIZE`). The read-receipt footer is `UserReadStatus` in all three menus: a divider, then an `li role=none`, rendered only for a seen message. It mounts only while its menu is open, so it fetches once per open. Its label is an `sr-only` "Seen by N". The long-press list is `role=menu` named "Message options", with `min-h-11` rows. Its rows are `MenuItem` rows on `useMenuList` (`ui/ContextMenu.tsx`), the engine that `ContextMenu` and `DropdownMenu` share, so the arrow keys, Home, End and typeahead work. A long press focuses the panel, as a right-click does. Every close returns focus to the element that had it, unless a row moved it. A long press can end in a click where the finger lifts. So a row runs only on a press that began on that row, or on Enter or Space. The right-click menu carries the same name through the required `aria-label` of `ContextMenu`. Shift+F10 or the Menu key opens it only while focus sits on a link, reaction or media control inside a `.msg_card`. A message card takes no focus, and the feed has no roving focus (#391). Escape closes it in a window capture listener that stops the event, so the composer does not also clear reply mode.
- **`Header` / `Footer` slots require stable, module-scope component refs; changing values flow through the `context` prop, NOT through closures.** Toggling the component reference itself (`Header={loadingOlder ? Loader : undefined}`) silently fails. Virtuoso re-mounts the slot, but the closure captured before the remount never updates. The inner spinner therefore never reaches the DOM, even though the `loading` state cycles correctly for the full RTT. `ChatList.tsx` defines `ChatListHeader` / `ChatListFooter` at module scope and adds `loadingOlder` / `loadingNewer` to `ChatListContext`. It reads them via `{ context }` in the slot props to drive `PaginationLoader` (top for older, bottom for newer). `MessageFeed.tsx` threads both flags through. Do not revert to inline-`useMemo` Header/Footer factories.

### Chatroom Realtime

- **Per-channel topic.** `useChannelRealtime` subscribes to `chatroom:${channelId}` for postgres_changes (INSERT/UPDATE on `messages`) plus broadcast events. Anon viewers receive the same events as authed — the source-table RLS (`messages_visible_select` / `messages_public_anon_select`) gates per-row, and anon's anon-JWT carries `role = 'anon'` so the `TO anon` policy matches. If realtime appears broken globally on `chatroom:*` topics, suspect `realtime.messages` RLS (`07-3-notification-broadcast.sql:109`) — a missing topic policy can block subscription authorization at the WS layer.
- **Own sends have no motion.** Their pending and failed look lives in `.cursor/docs/design-system.md` §MessageCard row. Do not animate Virtuoso item wrappers (they position via transform). `MessageCardProvider` stamps `data-status` (`pending` / `sent` / `failed`) on the card root only when the row has a `client_id`. The insert never writes `messages.client_id`, so server rows and merged echoes have none, and the stamp goes away when the echo lands.
- **Row-merge preserves RPC-computed columns.** `useChannelRealtime`'s drain uses `incomingRow.user_details != null` as the discriminator. Present → RPC-hydrated row (`fetch_message_window` / `fetch_messages_since`), authoritative. Absent → raw `postgres_changes` payload, graft `user_details` + `is_bookmarked` + `bookmark_id` from the existing in-memory row. Those columns are JOIN-computed in the RPCs, never on the `messages` table. So postgres_changes UPDATEs (reactions, edits, soft-deletes) can't carry them. Without the graft, reactions blank the avatar AND wipe the bookmark indicator. Both merge sites (UPDATE drain + optimistic→echo arrival merge) must stay in lockstep.
- **`newestSeqRef` null means "window not loaded".** The echo drain in `useChannelRealtime` waits while it is null. So the first window load (`useChannelMessages`) sets 0 for an empty window, not null; a later window replace (`applyWindowSeqRefs`) keeps the old value. With null, the first send in a new chat never merged its echo and stayed pending until a reload.
- **Catchup is paginated.** On `SUBSCRIBED` / `online` / `focus`, `useChannelRealtime.catchUp` loops `fetch_messages_since(p_since_seq = newestSeqRef)` until a page returns fewer than `CATCHUP_PAGE = 100` rows or `MAX_PAGES = 20` (2000-row cap) fires. A single-shot 100-row call silently drops gaps on busy channels after multi-hour disconnects. On cap-overflow the loop warn-logs and bails; the next user-initiated `snapToPresent()` resyncs from tail.
- **Soft-delete broadcast contract.** `handle_message_soft_delete` runs on the `NULL → NOT NULL` transition only. The `message_soft_delete` trigger carries a `WHEN (OLD.deleted_at IS NULL AND NEW.deleted_at IS NOT NULL)` clause, in lockstep with the sibling counter trigger in `09-message_counter.sql`. That clause gates the **whole** DEFINER cleanup body, not just the broadcast. A `deleted_at` no-op write (`PATCH {deleted_at:null}` on a live row) therefore can't fire it. It emits `realtime.send({id, channel_id}, 'message:deleted', 'chatroom:' || channel_id, FALSE)`. `private=FALSE` because anon viewers can't observe the postgres_changes UPDATE. The anon SELECT policy filters `deleted_at IS NULL`, so the realtime layer drops the event whose NEW row state fails the policy. Authed members receive both signals; `deleteBufferRef` is a `Set` so the duplicate is idempotent. The postgres_changes UPDATE for a delete carries no text. The BEFORE trigger `clear_deleted_message_text` nulls `content`, `html` and `medias` first (#435). Accepted, not fixed. (a) The id-only payload is readable by anyone holding the channel UUID, and any subscriber can also _forge_ a `message:deleted` on the public topic. Both are local-view-only: a forged prune self-heals on reload, and authed clients also get the authoritative postgres_changes UPDATE. The cheap client-side close, if ever wanted, is to ignore the broadcast when authed. (b) The unread decrement covers only members with an unread `notifications` row, a strict subset of the unconditional increment population. Online / muted / `notif_state≠ALL` members therefore drift upward. That self-heals on channel open via `advance_read_cursor`'s authoritative recompute. Topic and event name must not change without bumping the FE listener in `useChannelRealtime`.
- **Deep-link bridge.** `Chatroom.tsx` resolves the Virtuoso anchor as `deepLinkMessageId ?? store.chatRoom.fetchMsgsFromId ?? URL.msg_id`. All four in-app entry points (`BookmarkItem`, `hrefEventHandler`, `NotificationItem`, `useNotificationClickBridge`) feed `fetchMsgsFromId` through `setChatRoom`; shared links land via `?msg_id=`. Without any source, anchor falls back to `first_unread`. `useChannelMetadata` independently passes the same `startMsgId` to `fetchChannelInitialData` for anchor-existence validation. The duplication is intentional. It surfaces invalid deep-links as a user-visible error rather than silently falling back to tail.
- **Peer read cursor for sender check-marks.** Seed `peerReadSeq` from `get_channel_aggregate_data.peer_max_read_seq` at bootstrap; advance on private realtime topic `chatroom-read:{channelId}` event `read:advanced` (emitted by `advance_read_cursor`). `MessageSeen` uses `message.seq <= peerReadSeq` — do not drive check-marks from per-message `readed_at`. Reconnect catch-up re-seeds `peer_max_read_seq` via the same aggregate RPC (`useChannelRealtime.refetchPeerSeq` on the `online` window event).
- **`chatroom-read:{channelId}` topic split is load-bearing.** Two channels per chatroom: public `chatroom:{id}` carries postgres_changes + `message:deleted` broadcast (so anon PUBLIC readers receive them); private `chatroom-read:{id}` carries the `read:advanced` broadcast only. `realtime.send(..., 'chatroom-read:...', true)` requires the `chatroom_read_topic_access` RLS policy on `realtime.messages` (members-only via `substr(topic, 15)` → `channel_members.channel_id`). Folding `read:advanced` back onto the public topic leaks per-user read positions to anyone holding a channel UUID. Merging postgres_changes onto the private topic breaks anon PUBLIC-channel realtime. The FE `useChannelRealtime` subscribes both channels independently; the readChannel is gated on `currentUserId` (anon doesn't subscribe).
- **`peer_max_read_seq` is members-only.** `get_channel_aggregate_data` gates the `MAX(last_read_seq)` query inside `IF is_member_result THEN ... END IF;` so anon viewers + authed non-members on PUBLIC channels receive `NULL` — not a leak of who's actively reading. The corresponding FE seed in `bootstrapStore` ignores non-numeric values.
- **`advance_read_cursor` uses `FOR UPDATE`.** Without the row lock, two concurrent calls (open tab + mobile, double-click) can interleave SELECT/UPDATE and write a stale `unread_message_count`. The `greatest(last_read_seq, p_up_to_seq)` keeps `last_read_seq` itself monotonic, but the recomputed unread can flap. Pair the lock with the existing 1s FE debounce in `useReadCursor` — both layers are required.

### MessageComposer

- **Canonical row (mobile + desktop): `[ + ] field [ 😊 ] [ 🎤/✈ ]`** — no `@` or separate Aa/attach buttons in the row (type `@`; mention is also in the format toolbar). The left **`ComposerInsertMenu`** opens on click or tap, with no tooltip and no hover-open. Its panel is a dialog named `Insert`, with plain button rows, not a menu. Its rows are Attach file, Text formatting (toggles the format bar), and Record voice when send is showing. **`ComposerPrimaryAction`** switches mic ↔ ghost **`text-primary`** send when `canSend` — the same control species as + / emoji / mic, not a filled primary disc. It renders `null` during voice preview (the bar owns Send). **`VoiceNoteButton`** / **`ComposerOverflowMenu`** stay deleted.
- Voice: **`useVoiceRecorder`** + **`VoiceRecordingBar`** — hold to record; release sends. `useSendVoiceWhenReady` calls the normal `submitMessage` once the note's tile is ready. It sends only when that tile is alone and the editor is empty; otherwise the note waits for a manual Send. An error or a removed tile drops the pending send. A hold under 1 s, or a finger that leaves before the microphone answers (a tap, the permission prompt), sends nothing and shows the hold hint. If the microphone then refuses, the error toast shows instead. A tap never sends on a phone (maintainer ruling). Slide left cancels and slide up locks; the locked Stop and the 5-minute cap open the preview, whose Send sends. `stepVoiceNote` in `MessageComposer/helpers/stepVoiceNote.ts` owns every voice transition. `useVoiceRecorder` is its adapter over the microphone, `MediaRecorder`, timers and rAF. It runs the effects inside `dispatch`, in order, never in a `useEffect`. Every exit from recording or preview to idle runs the one `teardown` effect. `recorder.onstop` clears the timers before it dispatches, so a recorder that stops on its own leaks nothing. A drag move that crosses neither the lock line nor the cancel line keeps the same state object, so it does not re-render. The drag writes `--voice-drag-x`, `--voice-drag-y`, and `--voice-cancel-progress` on the composer root, never React state. Files are named by MIME (`voiceNoteFileName`), so iOS mp4 audio is stored as `.m4a`, not `.webm`. Starting a recording closes the other composer overlays (§MessageComposer overlay contention).
- **The mic needs a computed `touch-action: none`.** Without it, a slide is a browser pan: `pointercancel` ends the hold. An unlayered SCSS `touch-action` rule on composer buttons once beat the layered `touch-none` utility, so no slide ever worked. Do not add one back. The hold listeners follow the `pointerId` that pressed, so a second finger cannot move or end the hold.
- **Voice notes carry upload-time `duration` and a 40-bar `waveform`** (`readAudioShape` in `components/chatroom/utils/chatAudio.ts`, like image `width` and `height`). Only the sender decodes, at 8000 Hz; the feed never does. A voice note is a file named `voice-<epoch ms>.<ext>` (`isVoiceNoteName`), and the player hides that name. `parseAudioShape` checks both the insert and other clients' rows, and a waveform must have exactly 40 bars. `parseMessageMedias` and `messageMediasForInsert` copy known keys only, so a new media field must be added to both.
- **Activity chips.** `choosingEmoji` and `recordingVoice` ride the `typingIndicator` broadcast as `startActivity` / `stopActivity`. Only the composer emoji UI and voice recording send; reaction pickers never do. A start waits 300 ms, so a quick open and close sends nothing. The sender repeats it every 3 s. Peers expire it 8 s after the last start. That stays above two keepalives, so one lost resend keeps the chip. It lives in client-only `Profile.activity`, never in `status` (the Postgres enum `user_status`). One activity per face: the chip replaces the typing bounce. Anon matches typing: it never sends and never receives.
- Mobile composer dock steps off the feed: **`.composer-bar--mobile`** is `border-t border-base-300 bg-base-200` (feed stays `bg-base-100` paper) — never flat white-on-white. No format-panel fill of its own (inherits the well). Metrics: `items-center`, `min-h-11`, ProseMirror **`2.75rem`** scoped under that class (not viewport `sm:`). Touch targets via **`isMobile`** → 44px mobile / 32px desktop. Compact **`AttachmentStrip`**: each cell holds a 44 px tile (`size-11`) with full-tile Retry on a failed upload. A 44 px ghost Remove sits beside the tile, never on it, so the two targets do not overlap. Skeleton mirrors the same frame.
- Format toolbar: shared **`components/Toolbar/formatToolbarLayout.tsx`** — groups **B I S `</>` | Link @ | • 1. | Quote CodeBlock | Clear formatting**; mobile **`ComposerFormatPanel`** is a 6-column grid of two rows (#392); desktop uses inline **`FormattingToolbar`**; format tooltips use **`placement: top`**.
- Attach: **`useComposerAttachInput`** backs the Attach file row in **`ComposerInsertMenu`** — the sole attach entry point.
- After submit, `cleanupAfterSubmit` in `useComposerSubmit` decides the refocus. On a phone or tablet, `keepKeyboardAfterSubmit` (`isMobile`) is true, so the editor always refocuses. On desktop it refocuses only if the editor was the active element. Neither path refocuses while the emoji panel or the link dialog is open. Enter-key submits keep focus naturally.
- `useEditor(...)` in `components/chatroom/components/MessageComposer/hooks/useTiptapEditor.ts` is built once per mount. Its `onUpdate` reads `workspaceId` and `channelId` from `draftCtxRef.current`, and an effect keeps that ref current. Do not capture either id in the closure, or drafts cross channels.
- `prepareOutboundContent` must return stable `htmlChunks: string[]` / `textChunks: string[]` fields on both the happy and empty paths, so callers never need an `as` cast. It must not return a nested `chunks` wrapper.
- **Draft vs mode memory.** Text/HTML drafts live in IndexedDB (`messageComposerDB` via `syncComposerDraft` / `discardComposerDraft`). When IndexedDB fails to open, `messageComposerDB` keeps them in a module-level `Map` instead. Zustand `*MessageMemory` holds reply/edit/comment UI modes only — do not reintroduce `messageDraftMemory`. Edit and comment modes never write the saved draft. When either mode ends, the composer loads the saved draft again. An edit has its own attachment list under the `::edit` key, so an edit never touches the draft's attachments or their uploads. A comment shows the saved draft's tiles, but the files it adds never enter the saved draft. The draft key has no user id on purpose. Sign-out clears every draft through `clearAllComposerDrafts`, which cancels queued writes first, because the pagehide flush would write them back (#444).
- **Mode edges come from one table.** `useComposerModeEdge` turns the mode kind (`none`, `reply`, `edit`, `comment`) into one edge per change. The first edge of a mount starts from `mount`. The pure `composerModeEdgeAction` decides the draft load (`keep`, `fill`, `replace`) and the upload discard. `useComposerAttachmentLifecycle` reads that edge. `useComposerDraft` reads a second edge in which reply counts as none, so a reply toggle never re-runs the draft load. The draft load and the reply and comment upload discard come from the table; do not infer them from a previous-mode ref again. Leaving edit still cancels the `::edit` list through its own effect on `editMessageMemory`.
  - An edge that leaves reply or comment deletes the uploads that the mode added. A switch between reply and comment counts as leaving.
  - Entering a mode never discards, because the failed-comment restore records its files again after the `await`.
  - A mount discards only in none or edit. A mount in comment loads the saved draft, because closed unmounts the pane.
- **Post-send draft clear.** A successful send that is not an edit must call `discardComposerDraft` (cancels trailing debounced IDB writes, then deletes the row). An edit save keeps the saved draft, and ending the edit loads it back. A trailing debounced write after clear resurrects sent text when the user reopens the chatroom. The early clear deletes the saved draft, so `useComposerSubmit` reads it during the storage probe. A comment that fails writes it back, so a cancel loads the draft from before the comment. After the probe, the send reads the live mode from the store. If an edit or a comment started during the probe, the send leaves the editor alone and only deletes the saved draft.
- **Formatting toolbar session scope.** Toolbar defaults closed; expanded state is `sessionStorage` via `composerToolbarSession.ts` (per workspace+channel, current tab session only) — not IndexedDB.
- **Anon Enter opens sign-in.** `useComposerSubmit` calls `openComposerSignIn()` when `!user`; do not let Enter silently no-op for visitors. Never re-add `text` or `html` to the context type.

The old `usage` discriminator (`composer-inline | reaction | desktop`) and its central exhaustiveness `switch` are deleted; `Selector.tsx` reads only `{ variant, onSelect }` from `EmojiPanelContext` and never imports `useComposerEmojiPanelStore` or `emojiReaction`. - **Mention notifications (SQL).** A mention node in `messages.html` names its user by `data-id`, so a renamed user keeps the mention (#415). A null `html` uses the text rule alone. `internal.mentioned_user_ids` resolves mention nodes and typed tokens, and the mention and regular-message fan-outs both call it. The `@everyone` WHEN clauses keep their own copy of the token regex. `@everyone` still reads `messages.content` only. The three insert fan-outs in `10-func-notifications.sql` share one token rule. A token is `@` and then the longest run of `[A-Za-z0-9_-]`. The `@` is at the start or after a character outside that set. A token names a user only when it equals the username exactly, case included. So `@harvey` does not match `harvey_marzban`, `@bobSmith` does not match `bob`, and `bob@example.com` mentions nobody. The mention fan-out keeps channel members who have not muted the channel. It skips the sender and never resolves `everyone` to a user. `@everyone` fires only for the exact token. The regular-message fan-out skips a message only when it holds `@everyone` or a mention of a channel member other than the sender. A trigger `WHEN` clause cannot hold a subquery, so that member check runs in the function body. Membership alone decides it, so a mention of a muted member still gives other members no `message` row.

DOMPurify keeps `data-*` attributes by default, so mention spans keep `data-id` and `data-type`, and feed tap-to-profile via `useMentionClick` reads them. Only `class` is removed.
- A Postgres `42501` on `notifications` INSERT during an @mention send means a trigger function lost `SECURITY DEFINER` — see §Supabase.

### Anonymous Chat Read Path

- **Anon visitors get read-only PUBLIC chat, and only on a public document.** A Private document's chat, media and counts open only for its owner, through `internal.can_open_document` (§Supabase, #396). Anon can call every read path — `fetch_message_window`, `fetch_messages_since`, `get_channel_aggregate_data`, channel/user/message SELECTs — and hydrate the local Zustand store. The anon RLS policies and SQL functions handle `auth.uid() IS NULL` explicitly, so the read path renders cleanly without any FE early-return.
- **Media tiles need storage SELECT, not just message RPCs.** Anon lurkers and non-member authed viewers on PUBLIC channels resolve `createSignedUrl` against `storage.objects`. The `"Anon can read public channel chat media"` and `"Authed can read chat media"` policies in `12-buckets.sql` must qualify `objects.name` (see §Supabase → **`storage.objects` EXISTS subqueries**). Anon and signed-in non-members sign only an object that a live message names. Channel members sign every object in the channel (#432). Message hydration succeeding while thumbnails show `MediaUnavailable` usually means storage RLS denied the sign, not a webapp gate.
- **One resolve point maps a heading to its channel row (#402).** `useHeadingChannel` (in `Chatroom.tsx`) reads `channels` by `workspace_id` and `heading_id`. It creates the row only when the viewer may write, then reads again. It writes `chatRoom.channelId`: undefined while it resolves, null when the heading has no row. `ChatroomProvider` is keyed by that id, so every hook inside reads, writes and subscribes by the real channel id. Never read a channel by `id` with `chatRoom.headingId`. Keep `headingId` for presence, the TOC, the breadcrumb and share links. With no row, the provider gets `''`, makes no read and shows the empty feed; a visitor still gets the composer. A comment opened before the resolve waits under the heading id, and the resolve moves it to the channel id. Chat links go through `openChatFromLink` (`services/openChatFromLink.ts`). It opens a channel of this document by its `heading_id`, else a live toc-id or the documentId, else nothing. TOC badges read `resolveHeadingUnreadCount` (`utils/unreadDisplay.ts`), which maps a toc-id to its row. A visitor's count update carries no `heading_id`, so a heading created after the page loaded shows no visitor badge until a reload. A visitor who opens a heading with no row subscribes to nothing. A first post by someone else shows only after the visitor reopens the chat. Both gaps are accepted.
- **Writes must gate on `auth.uid()` at the entry point.** `useHeadingChannel` skips `upsertChannel`, `useChannelMetadata` skips `joinChannel`, `useSendMessage` short-circuits via `onAuthRequired`, and `useReadCursor.advance` no-ops when uid is null. Do not gate inside the RPC bodies; do not let RLS 403s reach the FE as toasts. Authenticated writes assume the channel/member rows exist.
- **Anon-only UI is hidden, not disabled.** The Bookmarks popover in `EditorToolbar.tsx` is gated `{user && <Popover>…</Popover>}`; `ChatroomToolbar/components/NotificationToggle.tsx` early-returns `null` when `useAuthStore.profile?.id` is falsy. Hide at the component (or wrapping popover) so the trigger never invokes an RPC that would 401 — don't render a disabled button that toasts on click.
- **Async-handshake success paths resolve their own state at the call site.** The `onAuthStateChange` handler intentionally omits `SIGNED_IN` from its store-writing branch. So a sign-in call that returns session data must finish the job itself: `GoogleOneTapAuth` writes `setSession`, toasts, fetches the profile, and applies the missing-row sign-out rule. **Centralising this on a guarded `SIGNED_IN` arm was evaluated on 2026-08-21 and rejected — do not re-propose it without new evidence.** Measured against `@supabase/auth-js` 2.112.3: `SIGNED_IN` re-fires from `_recoverAndRefresh` on every `visibilitychange` and again across tabs through BroadcastChannel, and on a PKCE return (Google redirect, magic link) `_initialize` schedules `SIGNED_IN` in a `setTimeout(…, 0)` while `_emitInitialSession` delivers `INITIAL_SESSION` for the same session. An identity guard cannot separate that pair — `useApi.request` has no in-flight dedupe, so the second event still sees a null profile and fires a **second** `getUserById`. One correction to the old wording: there is exactly one `TOKEN_REFRESHED` emit site and the refresh path emits no `SIGNED_IN`, so token refresh was never part of the thrash. **`router.reload()` is no longer the escape hatch** — call sites write the store directly. **`SignInForm` has no passkey path.** Passkeys are off (root `CLAUDE.md` §Settled). The email field sets `autoComplete="username"` with no `webauthn` token. **The webapp no longer signs visitors in anonymously** — production Auth forbids it, so a signed-out visitor reads through the `anon` role and its `*_public_anon_select` policies.
- **Anon viewers subscribe to the same `workspace:${workspaceId}` realtime channel** as authenticated users (handled in `useCatchUserPresences.ts`). Presence join/leave + broadcast events therefore flow into `useStore.usersPresence` and every `AvatarStack` surface: TOC header, TOC items, pad header `PresentUsers`, chatroom `ParticipantsList`, and message `UserReadStatus`. Each renders the same set of online users an authed viewer would see. Anon must NOT call `track()`: they observe only, never broadcast themselves into presence state. Do not split anon onto a separate `anonymous:*` channel — presence is per-channel-name and a parallel channel would silently miss every broadcast. **TOC heading avatars key on broadcast `channelId`, not native presence track.** Cold-open tabs (anon or authed) must handle `presence` `sync`. On subscribe / `requestPresenceSync` / peer `join`, existing viewers re-broadcast open chat via `shareHeadingPresenceWithRoom` in `services/workspacePresenceSync.ts`. That call carries a 600ms debounce per channel topic. Do not remove it, or late joiners miss heading stacks until someone switches chat. `buildPresenceSyncPayload` must seed the responder's open `headingId` into the sync payload when their row is missing from `usersPresence` (native Supabase presence track carries no `channelId`). **`settings.broadcaster`** is set only after a guarded authed `track()` in `useCatchUserPresences`, and cleared on effect teardown/offline. Chat open/switch uses `sendPresenceBroadcast` in `workspacePresenceSync.ts` (not a duplicate store helper).
- **`AvatarStack` consumers filter the current user out, never gate on `usersPresence.size`.** Authed `track(profile)` puts self in the map; anon never tracks so the map is already just other viewers. Size-based guards (`size <= 1`) hide the stack from anon when one auth peer is present. The right shape is `Array.from(usersPresence.values()).filter(u => u.id !== profile?.id)` then render when the remainder is non-empty — works for both auth (drops self) and anon (no-op). Stack cutout width is forced in `_daisyui.scss` (2px via `--avatar-stack-edge` from `avatarStackGeometry`). The reason is daisyUI `.avatar-group .avatar`, which ships `border: 4px` and beats Tailwind ring/border utilities. Use a cutout border, not a drop-shadow.
- **Clear `usersPresence` on every (re)subscribe.** `useCatchUserPresences` calls `clearUsersPresence()` at the top of its subscribe effect before opening either the anon or authed channel. This drops stale `ONLINE` entries from the previous channel (anon→authed sign-in, workspace switch, `online`-event reconnect). The next subscription's `presence` `sync` snapshot is then the authoritative state.
- **Anon's TOC badge re-purposes `unread_message_count` as a channel-activity hint** because anon has no per-user read cursor. Both `useMapDocumentAndWorkspace.fetchChannels` (initial) and `channelMessageCountsUpsert` (realtime) write `channel_message_counts.message_count` (channel TOTAL) into the store's `unread_message_count` field. This is intentional — don't "fix" it. Both write paths must auth-gate (`if (profile?.id) return`) so authenticated users keep the real per-user value from the `channel_members` subscription.
- **`fetch_message_window` returns `anchor_seq=null` for `first_unread` when no real unread exists** — anon viewers (no `channel_members` row) and authed users caught up to tail. SQL still windows around tail (so the view loads correctly); the FE only inserts the "Unread messages" sentinel when `win.anchor_seq != null`. Reverting this so anon/caught-up users see a sentinel before their tail message is a regression — the divider is meaningless without a read cursor.

### Chatroom Staged Skeleton

- The toolbar shell renders immediately; feed + composer show skeleton until bootstrap completes. The sole public gate is **`isFeedReady = isChannelDataLoaded && !messagesLoading && !errorMsg`** in **`ChatroomContext`** — **`initLoadMessages`**, **`isFeedLoading`**, and **`messagesLoading`** were removed from the context contract.
- During load, mount the real **`ChatList`** under an absolute skeleton overlay so Virtuoso **`listRef`** attaches (avoids a load deadlock).
- Skeleton palette covers the chatroom feed/composer and slug-page skeletons alike — see §Slug Page Entry And Skeletons. Use doc-style neutral **`.skeleton`** bars plus **at most one** pale `color-info` accent per feed via **`color-mix(in oklch, var(--color-info) ~18–20%, var(--color-base-300))`**. Never use media-tinted, bubble-shaped, or brand-colored media bones.
- Mobile: top-anchored scrollable ~15 rows; desktop: bottom-anchored panel. Modules live under **`components/chatroom/components/skeleton/*`**; breadcrumbs come from **`buildHeadingPath.ts`** / **`resolveHeadingBreadcrumbs()`**.
- On a channel data load error (`get_channel_aggregate_data`), the error wins over loading. The feed shows its error badge. `ChannelComposer` renders nothing: no field, no send button, no skeleton. `ParticipantsList` drops its skeleton and shows presence only. `isFeedReady` stays false on an error, so each consumer also checks `error`.
