# CLAUDE.md — @docs.plus/hocuspocus

Invariants for the collaboration server, the store worker, and the version store. Read [AGENTS.md](../../AGENTS.md) first — it holds the repo-wide rules (git policy, package manager, code quality, test policy) that still apply here. Sections §Hocuspocus Server and the rest of §Backend And Infrastructure now live in this file, below. The first four sections hold the rules the 2026-07-27 storage and persistence review established, each with the failure it prevents.

The storage design is settled and is not the thing to change: one full Yjs snapshot per version, one append-only `Documents` table. The whole live corpus is 1,280 kB on disk. Delta storage, Yjs V2 encoding, content-addressed rows, time partitioning, and moving blobs to object storage were each measured against real data and rejected. Do not re-propose one without new numbers. The binding ceiling is document-size-weighted concurrency — a loaded room costs 16.5–17x its stored snapshot in heap — not storage volume. The decision inverts only if the product ever needs every intermediate version retained, because retention thinning is what makes snapshot-per-version affordable.

## Persistence

- **Never `throw` out of the Database `store()` hook, and never out of its fallback catch** (`src/config/hocuspocus.config.ts`). Hocuspocus's `useDebounce` puts the in-flight promise in `runningExecutions` under `onStoreDocument-<docName>` and deletes it only after the await. The delete is therefore unreachable on rejection. The rejected promise stays cached for the process lifetime, every later `run()` re-awaits it, and the hook is never called again. `shouldUnloadDocument` ORs `isDebounced || isCurrentlyExecuting`, both stuck true, so the room's `Y.Doc` never unloads either. `server.destroy()` waits for `getDocumentsCount() === 0`, so it hangs past the 30 s `stop_grace_period` and SIGKILL takes `closeQueues()`, `shutdownDatabase()` and `flushObservability()` with it. One document's failed save destroys every other room's unflushed edits and loses the Sentry event that explains it. Measured: one rejection then eight keystrokes over 5 s produced 0 saves; 30 wedged rooms held 119.6 MB and `destroy()` was still hanging at 30.0 s.
  - **The trade is stated, not hidden.** The catch counts `document_store_rejections_total{reason="fallback-save-failed"}`, logs, captures to Sentry, and returns. That room loses its edits since its last successful save. Every other room keeps theirs.
  - **The counter is the only remaining trace.** Alert on `increase(document_store_rejections_total[10m]) > 0`. Without it the fix trades a permanent silent failure for a transient silent one.
  - **`captureDegraded` stays inside the inner `try`.** A throw out of the Sentry client escapes `store()` and wedges the debouncer by the identical mechanism.
  - **The swallowed double version collision `return`s.** Without the return the `'Document saved via fallback (direct DB)'` info line still fires after a dropped flush, which is a false success in the log stream. A second P2002 counts `reason="version-collision"`; anything that is not P2002 rethrows into the outer catch so a DB outage is still counted as `fallback-save-failed`.
  - **`server.destroy()` is bounded by a 25 s `Promise.race`** (`src/hocuspocus.server.ts`) against the 30 s grace. The shutdown tail therefore runs even if something else throws where this hook no longer does. Defence in depth, not the fix.

- **Merge raw, strip the result. Never strip before the merge, at any of the three append sites** — the worker INSERT (`src/lib/queue.ts`), the queue-down fallback (`src/config/hocuspocus.config.ts`), and `appendBackupRow` (`src/modules/document-versions/infra/versionsStore.ts`). `Y.mergeUpdates` takes struct content from the older head and only unions delete sets. Merging a stripped snapshot onto a raw head therefore carries text deleted inside a surviving parent forward permanently. `Item.gc()` keeps the `Item` and swaps its content to `ContentDeleted`. The comparator then sees Item-vs-Item, and sort stability hands the win to the older head. The strip's decode is the only thing that garbage-collects it. **This is a retention and right-to-erasure problem, not a storage one.** No API returns raw bytes — the exposure is dumps, backups, and direct DB access. Measured on the live corpus: 13 of 86 rows carried recoverable deleted prose, worst row 43,368 → 3,862 B (−91.1 %), visible state identical on all 13 after the fix. CPU is a wash (0.87–0.98x), so the extra decode inside the `FOR UPDATE` transaction costs nothing.
  - **`versionsStore.ts` re-encodes through a `Y.Doc` instead of importing `stripSnapshotMetadata`, on purpose.** `src/lib/queue.ts` opens a Redis socket and two BullMQ queues at module scope and throws when `REDIS_HOST`/`REDIS_PORT` are unset; REST must never load it. Do not "unify" the three sites onto one import. The caller already hands `appendBackupRow` a stripped snapshot, so the re-encode is the same primitive minus the metadata deletes it does not need.
  - **The fix is forward-only.** Rows written before it keep their ghosts. `scripts/backfill-strip-ghosts.ts` erases them — dry-run by default, `--apply` writes, `md5(data)`-guarded, each written row re-read and compared. It has run against the local database only; production rows still carry theirs. Filter on erasure, never on size: two carriers re-encode byte-neutral or slightly larger.

- **`rehostMediaUrls` (`src/lib/rehostMediaUrls.ts`) is a fourth site that re-encodes a snapshot through a `Y.Doc`, and it is not a unification candidate either.** It runs only in `duplicateDocument`, on the source's persisted head, before the copy has any row. The steps are: decode, repoint every `/hypermultimedia/<id>/<file>` URL onto the copy's own prefix, report the objects it saw, re-encode. The direction is the safe one — it re-encodes the OLDER head and nothing has been merged onto it yet. Verified on a real 77,433 B row. A later raw update (one block deleted, one appended) was merged onto the re-encoded head. That merge kept the later edit and held the block count at 313. It produced visible state identical to the un-rehosted live doc modulo the URL swap. It shares no primitive with the three append sites above. They merge raw then strip; this one rewrites content the merge has not seen. Folding them together buys nothing and re-creates the Redis-at-import problem.
  - **The URL names the prefix to copy from, not the source id, and the scan runs before the copy.** A live production row (`Zrl8S6a5609d4ViFEf5`) already carries its only media URL under a different document (`AwY06BK4pv671bffa6a`). Copying "the source's prefix" copies the wrong objects and leaves the copy pointing at a third document. Bounding the copy by what the snapshot names also stops a deleted media node's orphaned object from being resurrected under a new public URL. It also bounds N by what is live rather than by everything ever uploaded. The decode is gated on a raw-byte search for `/hypermultimedia/`. Yjs v1 writes attribute strings as literal UTF-8, so a snapshot without those bytes cannot name media.
  - **The duplicate's media re-host is forward-only.** Copies made before it still share their source's objects, so purging one of those sources still strips its copies. No backfill exists and none is planned; the decision is to fix the path and leave those rows. `scripts/e2e-duplicate-media.ts` pins the contract against real Postgres, the real Supabase purge RPC and real local storage.
  - **The dead-letter drain is a producer, not an append site.** `drainStoreDeadLetterQueue` (`src/lib/queue.ts`, driven by `scripts/drain-store-dlq.ts`) re-enqueues a stranded payload through `enqueueStoreDocument`, so the worker's `FOR UPDATE` merge stays the only code that writes the row. **Never "simplify" it into a direct insert.** The DLQ embeds the raw pre-strip state. An insert would therefore replace a newer head with an older snapshot, and store the ghosts the merge path exists to drop. Two consequences stay with the operator, and the script prints both. A row written after the entry failed usually already carries the stranded edits, so the replay mints a duplicate version. A duplicate carrying a `commitMessage` is exempt from `pruneAutosaveVersions` forever. An entry whose document has no rows left replays into `isFirstCreation`, which recreates the metadata row and fires `sendNewDocumentNotification` late. **A soft-deleted document's entry is removed, not parked.** Parking it was the bug. Nothing else clears a DLQ entry, so the reaper's later purge made the same entry flip from `skip-trashed` to `replay` on a fixed timer. The drain manufactured the one state it could not handle. For the same reason an entry whose `failedAt` predates `DOC_DELETE_RETENTION_DAYS` is refused outright rather than warned about. Past that window a document with no rows is indistinguishable from a first save lost in an outage.

- **Only a purge seals a room; a soft delete closes it but still flushes.** `purgeDocumentFootprint` publishes `{deleted, purged: true}` and `handleDocumentAccessEvent` (`src/lib/accessRealtime.ts`) adds the `Document` to `sealedRooms` only on `purged`, which makes `store()` drop the forced close-time flush. Sealing a soft delete too was a data-loss bug. Closing the last connection makes Hocuspocus run `executeNow`, so the drop cost every collaborator up to one debounce window (10 s idle, 60 s max). It prevented nothing either, because `isFirst` keys on the `Documents` table and a soft delete leaves those rows in place. `upsertDocumentMetadata` therefore takes its `update: {}` no-op arm. Restore cannot recover the dropped window; it returns the persisted state.
  - **The seal is published after the RPC and the media delete, and before the `deleteMany`.** Earlier and a purge that throws has already closed a room that survives — the client's `deleted` arm calls `stopReconnect()`, so nobody comes back. Later and the close-time flush re-creates the row the purge just removed.
  - **Two windows stay open.** `sealedRooms` is a per-process `WeakSet`. `publish` resolves on the Redis ack, not on the subscriber having run. A debounce firing inside that gap enqueues before the seal lands. And a job already in `wait` when the seal lands still reaches the worker's first-save branch. Both are as wide as queue latency.

## Retention and schema

- **`trigger` tells a row the server minted from a checkpoint a person chose.** `MACHINE_VERSION_TRIGGERS` (`src/types/queue.types.ts`) is `revert-backup` — the pre-restore safety copy in `versionsStore.ts` — and `schema-migration` — the one-time rebuild in `hocuspocus.config.ts`. The reaper's candidate predicate is `commitMessage IS NULL OR = '' OR trigger IN (…machine…)` (`src/hocuspocus.worker.ts`), so a machine-named row older than `DOC_AUTOSAVE_RETENTION_DAYS` is thinnable and a very old restore stops being undoable. That is the accepted trade. Before it, every restore minted two rows that no sweep could ever reach. Those rows were the only genuinely unbounded storage path in the system. A name a person typed stays exempt forever — `checkpoint`, `api`, and `revert` (the `Restored version N` row) are not machine triggers. Rows written before the column keep `trigger = null` and stay exempt.
  - **Never add a server-minted version row without a machine trigger**, and never widen the predicate by matching `commitMessage` text. The trigger column exists to remove exactly that fragility.

- **`@@index([documentId])` must stay. `@@index([documentId, version])` was the duplicate.** In that order, because two independent reviewers got it backwards and dropped the wrong one. `@@index([documentId])` is the narrowest documentId-leading cover for the version-list `count()`. Dropping it degrades that count from 8 buffers / 0.168 ms to 20 buffers / 0.332 ms. It is also the presorted key the reaper's Incremental Sort needs. `@@index([documentId, version])` was byte-identical to the index behind `@@unique([documentId, version])`: same columns, same order, same btree. It covered no read and cost a write on every save inside the `FOR UPDATE` transaction; dropping it took the reaper DELETE from 10.4 to 5.8 ms. Removed by `prisma/migrations/20260727090000_drop_duplicate_document_version_index`.
  - Do not justify the drop with `idx_scan=0`. The planner picks arbitrarily between identical indexes and a scratch replica chose the opposite one. The justification is that the two declarations were identical.
  - Keep that migration at exactly one statement. `DROP INDEX CONCURRENTLY` cannot run inside a transaction block, and Prisma's runner wraps a multi-statement file in one.

## Runtime limits

- **The REST server sets `idleTimeout: 60` explicitly** (`src/index.ts`). Bun's default is 10 s, and it closes the socket while the handler runs on to completion. A request that takes longer therefore reports failure over work that succeeded. Reproduced on Bun 1.3.14: the client failed at ~12 s with `request timed out after 10 seconds` and the duplicate still landed. `useDuplicateDocument.ts` has no dedupe, so a retry stacks a second full copy. The handler that reaches it is `duplicateDocument`, which copies every object its snapshot names, sequentially, inside the request. Bun caps this option at 255 s, so it is a ceiling, not a fix for an unbounded handler. A document whose media cannot be copied in 60 s still fails. The answer there is to move the copy off the request, not to raise the number.

- **The stateless default arm has a 64 KiB byte budget** (`MAX_STATELESS_RELAY_BYTES`, `src/hocuspocus.server.ts`). The arm re-stringifies the payload and mints one `OutgoingMessage` per connection, with no `readOnly` check and no throttle. `onAuthenticate` continues on a missing token and any public room is joinable with no credentials, so the sender is anonymous. Measured on a real 1024 M cgroup: one ~15 MiB frame to a 60-viewer room → OOMKilled, exit 137; a burst of 30 × 8 MiB to a 30-viewer room → exit 137. The amplifier is room size × burst rate, not frame size; the same burst under the budget peaked at 138 MB with no kill. Anything relayed through this arm that exceeds the budget is dropped with a warn, which is the point.
  - **`server.webSocketServer.options.maxPayload` is not the answer.** Bun ignores the `ws` option and caps frames at its own ~16 MiB, so setting it does nothing.
  - **The arm cannot be deleted.** The webapp sends `{ type: 'docTitle' }` through `titleWrite.sendDocTitleStateless` from `DocTitle.tsx`, `MobilePadTitle.tsx`, and the Documents rename hook; no named branch handles it, so it falls through to the relay. Deleting the arm breaks live document-title sync between collaborators. A `docTitle` payload is a title string, so 64 KiB is orders of magnitude of headroom.
  - **The arm relays `type: 'docTitle'` and nothing else, and refuses any payload carrying `msg`** (`RELAYABLE_STATELESS_TYPES`, `src/hocuspocus.server.ts`). The relay is unauthenticated and fleet-wide, so a client-chosen envelope was a client-chosen server event. `{type:'private'}` drove every viewer in the room through the webapp's `applyAccessStateless` → `exitSealedDocument` redirect. `{msg:'document:saved'}` flipped every viewer's status to "Saved" while their edits were still unpersisted. **An allowlist on `type` alone is not enough** — `useYdocAndProvider.ts` reads `msg` before `type`, so `{type:'docTitle', msg:'document:saved'}` passes a type-only guard. The named branches above own every legitimate `msg`. The guard runs ahead of the byte budget, so an oversized forgery counts as `type-not-allowed` and not as an OOM probe. It logs `String(type).slice(0, 64)` because the raw value is attacker-controlled and this file exists to stop an amplifier. No server event is affected: `readOnly`, `private`, `deleted` and `document:saved` all leave through `document.broadcastStateless` and never enter `onStateless`.
  - **`MessageType.BroadcastStateless` (6) is refused in `beforeHandleMessage`.** `MessageReceiver.apply` relays a type-6 frame to every room connection inline, so it never enters `onStateless` and the allowlist cannot see it. That path reaches only the local replica. It does not call `document.broadcastStateless`, so `beforeBroadcastStateless` never fires and `@hocuspocus/extension-redis` never publishes. The `onStateless` relay above does both and is therefore fleet-wide. The refusal drops that document connection with a CLOSE frame, not the socket. That is acceptable only because `@hocuspocus/provider`'s `MessageType` enum has no 6, so no shipped client can reach the close path. **If a future provider version adds one, change this arm before bumping.** `@hocuspocus/extension-redis` builds its inbound `MessageReceiver` with no `Connection`, so cross-replica `docTitle` sync never touches this hook.
  - **Both guards are pinned by `scripts/e2e-versions.ts` section `[8]`**, which keys every check on the `stateless_relay_dropped_total{reason}` delta. An absent broadcast alone also passes on a misencoded frame or a wrong room name. The counter is the only thing that proves the guard fired. `RedisExtension` is gated on `env === 'production'` (`src/config/hocuspocus.config.ts`), so that section proves the local room only. The fleet-wide reach of the relay arm comes from reading the library, not from the test.

- **`refreshPendingStateKeyTtls` derives the state key from the job id and `LRANGE`s the wait list** (`src/lib/queue.ts`). `enqueueStoreDocument` sets `stateKey = STATE_KEY_PREFIX + jobId` and passes the same value as `jobId`, so the key never needs the job hash. **Do not "improve" it back to `getJobs`.** Hydrating every job to read a derivable key cost +428 MB RSS at a 50,000 backlog. That cost lands inside the same 1024 M WS replicas that hold every loaded room, and `Bun.gc(true)` does not return it. Measured after: 11 ms / +21 MB against 318 ms / +330 MB.
  - **Paging `getJobs` with positive indices is worse than not paging.** BullMQ LPUSHes, so index 0 is the newest job with the freshest TTL and the tail is the oldest. A 20,000 budget over a 50,000 backlog re-armed the newest to 3600 s and left the oldest at ttl=100 s — precisely the loss this function exists to prevent. Deriving the key needs no cursor, so it cannot drift.
  - **Both `wait` and `paused` are read** because `Queue.pause()` RENAMEs one list to the other. The backlog answers to either name, and only one exists at a time.
  - **EXPIREs go out in 1000-key chunks.** ioredis buffers every queued command until `exec()`; one flat pipeline over 50,000 keys held +164 MB on its own.
  - Coverage is the `wait`/`paused` backlog — the worker-outage case this exists for. `delayed`, `active`, and `failed` jobs are no longer re-armed. Those lists are bounded (retry ladder, worker concurrency, `removeOnFail` 200 / 7 days). A job parked in one of them past the 1 h claim-check TTL loses its payload.

## Documented hazards we accept

- **A cross-replica `replace` can delete text the executing replica never saw.** `@hocuspocus/extension-redis` publishes document state from `afterLoadDocument` and `onChange` only — no timer, no anti-entropy — so convergence is edit-triggered. The handshake for the last edit before a quiet period can be lost (measured 21 delivered / 9 lost over 30 server-side kills). The replicas then stay divergent after Redis recovers, and the restore's `applyContentToDoc(doc, scratch, 'replace')` deletes only the blocks its own replica holds. Both replicas then converge on the wrong document. The window is bounded, not permanent. Hocuspocus defaults to `unloadImmediately: true` and the config does not override it, so a room unloads as soon as its last connection closes. This hazard needs a client continuously holding the stale replica. The pre-restore backup row is not compromised. `appendBackupRow` merges against the `FOR UPDATE`-locked DB head, so everything already persisted stays recoverable, stale only by the live debounce window. **We deliberately do not build for this.** Restore is reachable two ways, both landing on the same `applyContentToDoc`. The first is the service-role REST route. The second is the `history.revert` stateless op, which any authenticated writable connection can send — including the anonymous Supabase session every visitor gets. **The history sidebar now sends it.** `useVersionRestore.confirmRestore` (webapp) dispatches `history.revert` behind the Restore button, so this is a shipped path and no longer a hand-crafted frame. The maintainer accepted the hazard on 2026-07-29 rather than gate the feature. The pre-restore backup bounds the loss, the window needs a client continuously holding the stale replica, and both candidate fixes are rejected below. Re-open it if divergence is ever observed in production, not before. Room affinity via a Redis key is not the fix. Divergence requires both replicas hosting the room, so `afterLoadDocument` fires on both and the key names an arbitrary one, possibly the stale one.

- **A checkpoint can put its name on bytes the room has already moved past.** `HOCUSPOCUS_INTERNAL_URL` is a service name (`http://hocuspocus-server:4003`) and `docker-compose.prod.yml` runs that service at `replicas: 2`. The REST→WS hop therefore lands on an arbitrary replica. `internalHop` (`src/lib/internalHop.ts`) and both hop clients have no affinity, no retry and no room probe. Bun's `fetch` pools keep-alive sockets, so the replica is arbitrary once, then sticky. On a replica that is not hosting the room, `openDirectConnection` loads the persisted head. `@hocuspocus/extension-redis`'s `afterLoadDocument` then resolves without awaiting a peer's state. It resolves inside the `sub.subscribe` callback, right after an un-awaited `publishFirstSyncStep`. That is an internal of extension-redis 3.4.4 — re-read `afterLoadDocument` before bumping it, because the whole hazard derives from it. Two of the three arms are covered. The content apply accepts this in `API.md` (the `PATCH` concurrency note). The restore is the bullet above. It additionally commits `appendBackupRow` between the open and the commit — a DB round trip the other arms do not have. The checkpoint is what is new. Its commit is an empty `transact`, and `consumeVersionStamp` clears the stamp in `commit`'s `finally` (`src/modules/document-versions/infra/versionOps.ts`), before the disconnect flush. So the checkpoint's NAMED, retention-exempt row can be minted from pre-sync bytes. The room's converged bytes then land on a second row that is unnamed and therefore thinnable. `buildStoreJobId` fingerprints the state, so different bytes mint a different row. **It is latent, and it stays latent.** Both version write routes are `requireServiceRole` and no shipped client calls them. The history sidebar's Restore button reaches the revert through the `history.revert` stateless op, not through these routes. Unlike `history.revert`, a checkpoint has no stateless op: `checkpointOp` is reachable only from `document-versions`' HTTP controller. Revisit when the history UI ships a checkpoint action. **The obvious fix was tried and rejected; do not re-propose it.** Keeping the stamp alive across the disconnect flush does not correct the first row. It mints a second row carrying the same checkpoint name over different content, on every checkpoint, not sometimes. It also re-opens the retention hole the `trigger` column closed above. That row would be named with `trigger = 'checkpoint'`, which no sweep can ever reach. The queue-down direct-write path (`src/config/hocuspocus.config.ts`) writes each flush straight to Postgres with no job id and no dedupe. With the queue down, every checkpoint would leave two permanently exempt rows. A convergence barrier is not the fix either. There is no signal to await, `afterLoadDocument` resolves before any peer replies, and on a cold document no peer exists at all. A wait would therefore be an unmeasured sleep that shifts a probability.

### HTTP Modules

- **House envelope** (`ok` / `fail` / `houseEnvelopeHook`) lives in `apps/hocuspocus.server/src/http/envelope.ts`. Content, conversion, versions, documents, admin, and email import it from there. Do not re-home it inside a feature controller. Do not re-export it from the content controller. `validationFailed` is not a public helper; the hook inlines that 400. Every `zValidator` passes the hook except a domain-specific 400 (link-metadata `INVALID_URL`). Do not force the hook onto that route.
- New backend HTTP features go to the `hocuspocus.server` app (`@docs.plus/hocuspocus`, Hono), not webapp `pages/api/`.
- New endpoints live under `apps/hocuspocus.server/src/modules/<feature>/`:
  - `domain/`: pure logic and pipeline stages.
  - `http/`: controller, router, zod schema.
  - `infra/`: Redis cache and external SDK adapters.
  - `__tests__/`: unit and integration tests.
- A `module.ts` exports `init({ deps }): { router }`.
- A module may additionally export an `initWs*(deps)` factory returning `{ app, … }` when a feature needs an endpoint inside the WS process. `document-content`'s `initWsApply(deps): { app }` is the precedent. Content injection must run where the live Y.Doc is, so the collaboration process serves that app on its internal listener.
- `src/index.ts` mounts with `app.route('/api/<path>', module.init({ ... }).router)`.
- Modules must have no top-level side effects.
- **`document-conversion` writes no content.** Export renders the persisted head. Import returns Tiptap JSON, and the caller applies it through `PATCH /content`, the only write path that enforces the read-only lock (`hocuspocus.server.ts`). Persisting inside import routes around that lock and silently edits locked documents. It is not side-effect free: `infra/imageUpload.ts` rehosts embedded Word images to object storage, so a discarded import leaves orphans. Say "no database write, no content mutation", never "nothing is written".
- **DOCX export takes the socket away from the converter (`@turbodocx/html-to-docx`), and the order is load-bearing.** The origin allowlist runs first (`mediaPublicBaseUrl`, in `renderDocumentHtml`). That src is ordinary pad content any editor can set, so a service-role export would otherwise fetch cloud-metadata or intranet URLs on demand. Only an origin allowlist holds, because the converter follows redirects past anything a denylist could refuse. `inlineExportImages` then fetches each survivor itself and inlines it as a `data:` URI, so the converter never opens a connection. **Origin first, bytes second — reversed, the sniff in `inlineExportImages` becomes the SSRF the origin allowlist exists to prevent.** ODT degrades images to links and Markdown never fetches, so this stays a DOCX-only concern.
- **Only bytes positively identified as PNG or JPEG reach the converter** (`apps/hocuspocus.server/src/modules/document-conversion/domain/inlineExportImages.ts`). The converter bundles `image-size@2.0.2`, whose ICNS, HEIF and JXL parsers loop forever on a crafted header. The loop was measured at ~1.3 GB/s allocation, and it is synchronous, so it wedges every REST route and then OOM-kills the container. `image-size`'s own `catch` cannot see it. No upstream patch exists; both advisories are waived in `.github/audit-allowlist.json` on the strength of this boundary, so **deleting the sniff silently un-fixes them**. The drop is the default arm because the detector tries every parser it has on bytes it cannot place. Merely-unrecognised input still reaches those loops. **Inlining alone closes nothing** — the `data:` branch reaches `image-size` too, verified by execution. Sniffing at upload does not work either: the upload gate deliberately allows `image/heic` and `image/heif`. The sniff drops GIF and WebP for a second, unrelated reason. The converter's `[Content_Types].xml` is a hard-coded literal declaring only `rels`, `jpeg`, `png`, `svg` and `xml`, so a `.gif` or `.webp` part is OPC-invalid. Those images were already exporting into a package Word refuses to open, so dropping them removes broken behaviour rather than working behaviour. **`[Content_Types].xml` declares SVG, and it did export correctly. The sniff drops it deliberately, and these advisories are not the reason.** `buildImage` special-cases `isSVG` and takes dimensions from the node's own `width`/`height` without ever calling `image-size`, so SVG never reached the looping parsers. The sniff drops SVG for two reasons. A magic-byte allowlist has no signature to match text on. SVG is also script-bearing: `storage.s3.ts` already forces it to download rather than render at the media origin. Re-allowing it through a text-shaped check would reopen that question, not the advisories. It is the one genuine user-visible loss.
- **Three caps bound one export, and each exists because we measured the version without it failing.** `inlineExportImages` charges `MAX_EXPORT_INLINED_BYTES` **per `<img>`, not per URL**. The converter writes one media part per node, so N nodes sharing one src put N copies in the HTML string. Metering unique fetched bytes let two nodes reach +670 MiB against `rest-api`'s 512M cgroup. `MAX_EXPORT_IMAGES` caps both inlined elements **and**, through `fetched.size`, the number of sockets one export opens. That second term is load-bearing and non-obvious. A failed fetch charges no bytes and inlines nothing, so without it a document of dead URLs dials out unbounded. `EXPORT_IMAGE_TOTAL_TIMEOUT_MS` is the wall clock, read before each fetch, so the true cap is it plus one in-flight image. **Bytes alone can never end the run.** The remainder only decreases when `inlineExportImages` charges an image, so it settles on a small positive residue. A `cap <= 0` test is therefore unreachable. That exact guard shipped once and never fired. Fetching is serial for the same reason: a pool lets several fetches read the remainder before any subtracts.
- **`zipInflateSize` measures inflation, it does not read the declared size.** `MAX_IMPORT_BYTES` caps the compressed body; mammoth's unzip has no cap of its own, and 200 KiB of deflated padding reaches 200 MiB. The check walks the ZIP central directory and actually inflates each entry through `inflateRawSync({ maxOutputLength })`, abandoning the upload the moment the running total passes `MAX_INFLATED_IMPORT_BYTES`. **Declared sizes are not evidence and must never be trusted here** — a bomb states whatever it likes. A 299 KiB archive declaring 1 KiB while truly inflating to 300 MiB was accepted by the old declared-size version. This version refuses it (measured 2026-07-25, 0.09s). Cost on real files is negligible — 1.4 ms for a 5 MiB deflate entry, 0.1 ms for a 116 KiB stored `.docx`, verified byte-exact against `unzip -l`. This became load-bearing when import stopped being service-role-only: any signed-in caller, including a self-serve anonymous session, can now reach the converter. An unreadable or unknown-method container returns `null` and defers to the converter, which fails the upload as `422` anyway.
- **Clamp anything a stored attribute multiplies.** `encodeContent` validates content expressions, not attribute values, so `colspan` arrives unbounded. `odtExport`'s `MAX_TABLE_SPAN` is what stops one poisoned cell re-allocating gigabytes on every later export of that document.
- **XML 1.0 forbids control characters outright**, so `docxExport` strips them from both the HTML and the core-property title. The library xmlbuilder2 throws on one, which turned a single pasted character into a permanent 500 on every DOCX export of that document. `odtExport.escapeXml` owns the same rule for ODF.
- **The conversion module derives its own render and parse schemas** (`domain/conversionSchema.ts`) from the shared migration set. See §Document Model And Migrations before touching `lib/migration-extensions.ts` for a rendering fix.
- **`<a href>` binds to `link`, not `hyperlink`, unless StarterKit's link is disabled on the parse variant.** Both claim `a[href]` and neither declares a priority, so StarterKit wins and imported links land on a mark the editor cannot edit. `getParseSchema()` disables it; markdown import shares the export manager and still produces `link` — a known divergence, not a blocker, because `encodeContent` accepts both.
- **One `MarkdownManager` per process** (`getMarkdownManager()`, `domain/markdownExport.ts`). Constructing a second mutates the global `marked` singleton and its handlers accumulate rather than replace, so a per-call manager leaks unboundedly in a long-lived process. Import parses through the export instance.
- **`MAX_MARKDOWN_CHARS` (64 KiB) is a reject, never a truncate.** `marked` parses in quadratic time — 64 KiB takes ~0.6 s, 954 KiB blocks the event loop for ~144 s — and half a document is worse than a refused one.
- The link-metadata feature was migrated out of `webapp/src/pages/api/metadata.ts`; do not reintroduce server endpoints there.
- Link-metadata vocabulary is `stage`, never `tier`.
- Stages are cache -> oembed -> special (host handlers) -> htmlScrape -> fallback.
- `STAGE_TIMEOUT_MS` and the base User-Agent constant live in `domain/types.ts`.
- Host handlers live under `domain/stages/handlers/`.
- `htmlScrape` appends `facebookexternalhit/1.1`; Reddit uses the plain base UA `DocsplusBot/1.0`. Keep them intentionally different.
- Test files mirror source filenames one-to-one, e.g. `htmlScrape.ts` -> `htmlScrape.test.ts`.

### Hocuspocus Server

- **The persistence, retention and runtime invariants live in this file's first four sections** (§Persistence, §Retention and schema, §Runtime limits, §Documented hazards we accept). The 2026-07-27 storage review established them, each with the failure it prevents. Read them before touching the store hook, the worker, the reaper, or the version store.

- `HOCUSPOCUS_THROTTLE_BANTIME` is **minutes** (`@hocuspocus/extension-throttle` multiplies ×60×1000 — `60000` ≈ a 41.7-day ban).
- The BullMQ `store-document` `jobId` includes a Yjs state fingerprint so a final disconnect flush is not deduped away inside the 10s window.
- Pad editor file uploads hit `POST /plugins/hypermultimedia/:documentId` — the cap is `DO_STORAGE_MAX_FILE_SIZE` (bytes) on `rest-api`; canonical **`10485760`** (10 MB, matches `mediaUploadLimits.ts`). Mis-set **`0`** or tiny values like **`4000`** (~4 KB, a port/unit mix-up) yield `PAYLOAD_TOO_LARGE` / "0.00MB max". Verify live via `docker compose … exec rest-api env | grep DO_STORAGE_MAX_FILE_SIZE` (`.env.production` on the server is source of truth; `Notes/` backups may differ).
- Compose gives shell env vars precedence over `--env-file`, and a running container keeps its baked value until recreated. A corrected env therefore only takes effect on `up -d --force-recreate rest-api` (or the next deploy).
- `media.service.ts` `resolveMediaMaxFileSize` **floors any value under 1 MB** (`MIN_PLAUSIBLE_MEDIA_MAX_FILE_SIZE`) to the 10 MB default with a startup warn. A mis-set env can no longer brick uploads. `env.schema.ts` still coerces `0`/invalid as the outer layer.
- **The Database `store()` hook never decodes the snapshot.** It reads `isDraft`/`commitMessage` O(1) from the live `data.document` metadata map; the Yjs decode + metadata strip (`stripSnapshotMetadata`) runs in the worker. Do not reintroduce `Y.applyUpdate`/`Y.encodeStateAsUpdate` on the WS store path — it blocks the event loop for every connection (the 2026-07-08 persist-p99 rework).
- **Draft identity is anchored on first edit.** A never-persisted draft's `documentId` is BOTH the client `IndexeddbPersistence` key AND the Hocuspocus room name. That id is derived from the slug by `createDraftDocument` in `documents.service.ts` — `deriveDocumentId(slug, epoch)`, NOT random. Before the first persist, a reload used to mint a NEW id, rotate both keys, and orphan the early edits. That is the blank editor, the "content-disappear" class. `firstEditMetadataExtension.onChange` (`hocuspocus.server.ts`) closes it. On the first `isDraft` → `false` flip it eagerly writes the slug→`documentId` `DocumentMetadata` row via `ensureDraftDocumentMetadata`. That write is idempotent — `P2002` = already anchored, or a concurrent first-open won the still-`@unique` slug and we cede. It is WeakSet-guarded once per loaded Document (keyed by the Document object → auto-GC on unload, no per-keystroke writes). It anchors IDENTITY only; content/versions still persist via the debounced `store()`. **The worker's `upsertDocumentMetadata` must never OWN metadata — its UPDATE branch is `update: {}` (no-op); CREATE is the sole no-row backstop.** A content persist re-asserting `title=slug`/`ownerId` on the first version reverted a user-set title to the slug on reload. It could also flip ownership to the last flusher. The anchor, the `updateDocument` PUT and `createDocument` are all more authoritative. So a reload's `getDocumentBySlug` returns the same id → same IndexedDB + room → the mirror restores the edits. Full-stack regression coverage is `apps/webapp/cypress/e2e/document/draft-first-edit-anchor.cy.ts`. It asserts that the draft survives a pre-debounce reload, and that no row is written without an edit. It also asserts that a renamed title survives the first persist, and that every first-open of one new slug gets the same `documentId`. The spec is real-stack, DB-asserted via `docker exec` `psql` cy.tasks against `docsy-postgres-local`, and needs `make dev-local`. Bots that open and never edit keep `isDraft` and stay row-less (anti-empty-doc).
- **A draft's `documentId` is DERIVED from its slug, not random** (`lib/documentId.ts`, `deriveDocumentId(normalizedSlug, epoch)` = base62 of `sha256`, 19 chars). Random ids gave two people opening the same new slug two different rooms. They never saw each other, and the loser's text persisted under a suffixed slug no URL reaches. This happened in production on 2026-07-22 and 2026-07-24 — the `25P02` DLQ entries. Deriving makes the cede in `ensureDraftDocumentMetadata` correct rather than lossy, because the winner's row already holds the id this session is using. **Base62 and 19 chars are load-bearing**: `lower(documentId)` is stored in `workspaces.slug`, CHECKed against `^[a-z0-9]+(?:-[a-z0-9]+)*$`, so base64url fails on `_`. Existing documents keep their random ids forever. `getDocumentBySlug` runs first and `createDraftDocument` is only reached when no row exists, so there is no backfill and the population stays mixed. Guessability is accepted. No endpoint is protected by id-unguessability (WS is `resolveWsAccess`, content REST is `requireServiceRole`, the rest is `requireUser`). For a public document the slug already grants everything the id grants. Two paths still mint a random id and are meant to. The first is `createDocument` (the authenticated create writes its row immediately, so it has no race). The second is a slug that `slugify` reduces to nothing. That one can still fork, unchanged, and the anchor never writes for it either.
- **The purge epoch is what makes that safe.** `DocumentSlugEpoch` is bumped inside the same transaction as the `DocumentMetadata` row delete in `purgeDocumentFootprint`. Without it a purged slug would derive the erased document's id. A returning visitor's stale `IndexedDB` mirror on that key could then sync erased content back up. That is a right-to-erasure failure, not just a duplicate. Bumped only when a row actually went, so a no-op purge cannot rotate a live document's id. A slug with no epoch row derives at epoch 1.
- Residual: a sub-second window before the anchor's `onChange` → DB write lands. There is also a rolling deploy window where one replica still mints random ids while another derives. That window is bounded by the deploy, and the outcome is the old behaviour, not worse.
- **Document state rides a claim-check Redis key** (`store-doc-state:<jobId>`, 1h TTL, binary — no base64); BullMQ job data carries only `stateKey`. The worker still accepts legacy inline `state` (in-flight jobs across deploys). The DLQ handoff embeds the base64 payload, so recovery survives the key TTL. That holds only when the worker held the state at failure time. A job that sits in `wait` past the TTL before its FIRST attempt (worker outage or deep backlog) would dead-letter payload-less. The store()-side direct-DB fallback does not cover this either. It fires only when enqueue throws, not when the worker is down. Closed after the 2026-07-14 outage by `refreshPendingStateKeyTtls` (`lib/queue.ts`). The WS server (producer side, where enqueue lives) re-arms pending jobs' state-key TTLs every 10 min, covering the `wait` and `paused` lists. `Queue.pause()` RENAMEs one to the other, so the backlog answers to either name. `delayed`, `active` and `failed` are deliberately not re-armed (see §Persistence above). Those lists are bounded, but a job parked in one past the 1h TTL still loses its payload. Keys stay TTL'd so volatile-lru under OOM remains the accepted backstop loss path.
- **Producer-only Redis `commandTimeout` is 5s** (`lib/queue.ts`) so a wedged Redis fails into the direct-DB fallback fast. Never lower the global `REDIS_COMMAND_TIMEOUT` — it races the workers' blocking `bzpopmin`.
- **Worker (blocking) Redis connections use `bullmqWorkerConnectionOptions`** (`lib/redis.ts`): no `commandTimeout` at all and a retryStrategy that never returns `null`, even in dev. The dev fail-fast retryStrategy permanently killed the `bzpopmin` client after a macOS sleep/wake (2026-07-14). `bullmq` ≥5.79 swallows the connection error and parks the fetch loop at `blockUntil=Infinity` with `isRunning()` still true. The worker looks healthy (`/health` green) while every save strands in `wait` until the claim-check TTL destroys the payload. Do not hand a blocking client the shared fail-fast options; verify liveness with `redis-cli CLIENT LIST | grep -c bzpopmin` (expect 3: document/email/push). The worker `/health` additionally gates on dequeue-liveness (`getStoreQueueOldestWaitingAgeMs` < 120s — retries back off in `delayed`, so the ladder can't trip it). The prod container healthcheck consumes that status, so a parked fetch loop flags unhealthy in ~1 min instead of hiding.
- **BullMQ `attemptsMade` counts prior attempts inside the processor** (incremented in `moveToFinished`, after the throw), so every DLQ condition is `attemptsMade + 1 >= attempts` (document, email, push queues alike).
- **Autosave retention exempts the names a person typed, not every `commitMessage`.** The worker's hourly cleanup thins autosave rows older than `DOC_AUTOSAVE_RETENTION_DAYS` (default 30, `0` disables) to one per document per day. Its predicate is `commitMessage IS NULL OR = '' OR trigger IN (…machine…)` (`hocuspocus.worker.ts`). So a `checkpoint`/`api`/`revert` row and any pre-column `trigger = null` row stay forever. A `revert-backup` or `schema-migration` row is thinnable, even though both writers stamp a `commitMessage`. The trade is in §Retention and schema above — do not narrow the predicate back to the `commitMessage` test.
- Latest-version lookups use `ORDER BY version DESC` (served by the `(documentId, version)` unique index); `ORDER BY id DESC` has no supporting index and scans every version row.
- **`get_cron_job_health` is a single-pass aggregate** (`scripts/16-cron-jobs.sql`) and the worker samples it every 60 s (`CRON_HEALTH_SAMPLE_EVERY_TICKS` in `workerMetricsSampler.ts`), not on the 15 s queue tick. Do not revert to per-job correlated subqueries or per-tick sampling — 26 seq scans of `cron.job_run_details` per call every 15 s was prod's #1 self-inflicted DB load (2026-07-17 audit).
- **BullMQ custom jobIds are colon-free, always.** `':'` is BullMQ's Redis key separator and `validateOptions` throws on it. This silently disabled the entire store queue once bullmq ≥5.79 landed: every save fell back to the inline WS-loop write. `buildStoreJobId` in `lib/queue.ts` owns the store format; e2e must use it, never a hand-rolled id.
- **Hocuspocus v3 `onAuthenticate` payload field is `connectionConfig`** (the v2 `connection` was renamed; destructuring `connection` is silently `undefined`). Server-side readOnly enforcement sets `connectionConfig.readOnly = true`; keep the payload typed as `onAuthenticatePayload`, never `any`.
- Both version-append paths (the worker INSERT and the queue-down inline fallback in `store()`) merge the snapshot with the locked head row (`Y.mergeUpdates`). An out-of-order commit or a divergent concurrent fallback can therefore never clobber newer edits into the latest version. Keep them in lockstep — do not let one merge and the other plain-insert.
- `stopOnSignals: false` stays in the Hocuspocus config — the app's `shutdown()` owns SIGTERM ordering; the library's own handler `process.exit(0)`s before the queue/DB/observability cleanup tail.
- The `ENABLE_SCHEMA_MIGRATION` fetch path must persist the rebuilt snapshot (`persistMigratedSnapshot`, FOR UPDATE + advance/P2002-aware). Serving an unpersisted rebuild lets IndexedDB-cached clients merge two independent CRDTs and duplicate the document.
- **Port 4003 is the WS process's internal HTTP listener** — Prometheus `/metrics` plus two service-role write paths. Those are the content apply (`POST /internal/documents/:documentId/content`) and the version ops app (`documentVersions.initWsOps().app` — checkpoint and restore, the restore reaching the same `applyContentToDoc(…, 'replace')`). The listener is bound via `HOCUSPOCUS_INTERNAL_HTTP_PORT` / `HOCUSPOCUS_INTERNAL_HTTP_HOST`. The host default is `0.0.0.0` on purpose. Prometheus scrapes it cross-container by DNS discovery. `infra-target-down` pages when the `hocuspocus-server` scrape job is `up==0`. A loopback default would silently kill every WS metric the moment the compose env went missing. Never Traefik-route it; REST reaches it through `HOCUSPOCUS_INTERNAL_URL`. Open work sits in [`BACKLOG-hocuspocus-backend.md`](../../BACKLOG-hocuspocus-backend.md).
- **Content injection flows only through `openDirectConnection` + `transact`, and REST never imports `src/lib/queue.ts`.** That import opens a Redis socket and two BullMQ Queues at module scope. It throws outright when `REDIS_HOST`/`REDIS_PORT` are unset. The WS hop is what keeps it out of the REST process and out of `bun test`. **Unit tests that mock the store queue must type against `src/types/queue.types.ts` (e.g. `EnqueueStoreDocumentParams`).** **Never import `src/lib/queue.ts` for types alone**, or evaluating the module opens Redis before `mock.module` runs and the no-infra gate fails.
- **`encodeContent` is the single fail-closed choke point for injected content.** It enforces `MAX_CONTENT_NODES` (50 000) and `MAX_CONTENT_DEPTH` (100) through one **iterative** pre-walk before `TiptapTransformer.toYdoc`. Never use recursion there, or the walk overflows on the very input it exists to reject. It then stamps `toc-id` on heading/table nodes that lack one or duplicate one (first occurrence in document order keeps the id). It then enforces the title-first rule, and then checks content expressions against an authoring schema. That order is what a 422 reports: a payload failing both gates returns the title-heading detail and never the schema one. `applyContentToDoc` clones every node before it touches the live fragment. `clone()` recurses, so a throw has to land while the fragment is still whole. Otherwise collaborators see a half-wipe.
- Prod deploy order: `hocuspocus-worker` (scale 2, matching compose replicas) before `hocuspocus-server`, and `hocuspocus-server` before `rest-api`. Consumers learn a new job or wire shape before producers emit it.
- **A service-role write carries the operation, never a person.** Two column classes, and the class decides. A claim column answers "who did this" — `Documents.triggeredBy`, `DocumentClientAuthor.userId`, a chat message author. Only a party that really acted may be named. So a REST write sets the actor to an explicit `null`, and `trigger` carries the meaning (`document-content/http/controller.ts:199-200`). A grant column answers "who this belongs to" — `DocumentMetadata.ownerId`. The caller decides it, the server stores it verbatim, and only the service-role key may set it (`documents.controller.ts:154-165`). This upholds the `user=` audit-param cut at `PROMPT-inject-content-rest-api.md:238`. It does not reopen it. The block-authorship half is at `apps/webapp/CLAUDE.md:223`, so do not restate it here. Never mint a bot user row to stand in for a caller on a claim column.
