# CLAUDE.md — @docs.plus/hocuspocus

Invariants for the collaboration server, the store worker, and the version store. Read [AGENTS.md](../../AGENTS.md) §Hocuspocus Server first — it holds this package's general rules and is not repeated here. This file holds the rules the 2026-07-27 storage and persistence review established, each with the failure it prevents.

The storage design is settled and is not the thing to change: one full Yjs snapshot per version, one append-only `Documents` table. The whole live corpus is 1,280 kB on disk. Delta storage, Yjs V2 encoding, content-addressed rows, time partitioning, and moving blobs to object storage were each measured against real data and rejected. Do not re-propose one without new numbers. The binding ceiling is document-size-weighted concurrency — a loaded room costs 16.5–17x its stored snapshot in heap — not storage volume.

## Persistence

- **Never `throw` out of the Database `store()` hook, and never out of its fallback catch** (`src/config/hocuspocus.config.ts`). Hocuspocus's `useDebounce` puts the in-flight promise in `runningExecutions` under `onStoreDocument-<docName>` and deletes it only after the await, so the delete is unreachable on rejection: the rejected promise stays cached for the process lifetime, every later `run()` re-awaits it, and the hook is never called again. `shouldUnloadDocument` ORs `isDebounced || isCurrentlyExecuting`, both stuck true, so the room's `Y.Doc` never unloads either. `server.destroy()` waits for `getDocumentsCount() === 0`, so it hangs past the 30 s `stop_grace_period` and SIGKILL takes `closeQueues()`, `shutdownDatabase()` and `flushObservability()` with it. One document's failed save destroys every other room's unflushed edits and loses the Sentry event that explains it. Measured: one rejection then eight keystrokes over 5 s produced 0 saves; 30 wedged rooms held 119.6 MB and `destroy()` was still hanging at 30.0 s.
  - **The trade is stated, not hidden.** The catch counts `document_store_rejections_total{reason="fallback-save-failed"}`, logs, captures to Sentry, and returns. That room loses its edits since its last successful save. Every other room keeps theirs.
  - **The counter is the only remaining trace.** Alert on `increase(document_store_rejections_total[10m]) > 0`. Without it the fix trades a permanent silent failure for a transient silent one.
  - **`captureDegraded` stays inside the inner `try`.** A throw out of the Sentry client escapes `store()` and wedges the debouncer by the identical mechanism.
  - **The swallowed double version collision `return`s.** Without the return the `'Document saved via fallback (direct DB)'` info line still fires after a dropped flush, which is a false success in the log stream. A second P2002 counts `reason="version-collision"`; anything that is not P2002 rethrows into the outer catch so a DB outage is still counted as `fallback-save-failed`.
  - **`server.destroy()` is bounded by a 25 s `Promise.race`** (`src/hocuspocus.server.ts`) against the 30 s grace, so the shutdown tail runs even if something else throws where this hook no longer does. Defence in depth, not the fix.

- **Merge raw, strip the result. Never strip before the merge, at any of the three append sites** — the worker INSERT (`src/lib/queue.ts`), the queue-down fallback (`src/config/hocuspocus.config.ts`), and `appendBackupRow` (`src/modules/document-versions/infra/versionsStore.ts`). `Y.mergeUpdates` takes struct content from the older head and only unions delete sets, so merging a stripped snapshot onto a raw head carries text deleted inside a surviving parent forward permanently. `Item.gc()` keeps the `Item` and swaps its content to `ContentDeleted`, so the comparator sees Item-vs-Item and sort stability hands the win to the older head; the strip's decode is the only thing that garbage-collects it. **This is a retention and right-to-erasure problem, not a storage one.** No API returns raw bytes — the exposure is dumps, backups, and direct DB access. Measured on the live corpus: 13 of 86 rows carried recoverable deleted prose, worst row 43,368 → 3,862 B (−91.1 %), visible state identical on all 13 after the fix. CPU is a wash (0.87–0.98x), so the extra decode inside the `FOR UPDATE` transaction costs nothing.
  - **`versionsStore.ts` re-encodes through a `Y.Doc` instead of importing `stripSnapshotMetadata`, on purpose.** `src/lib/queue.ts` opens a Redis socket and two BullMQ queues at module scope and throws when `REDIS_HOST`/`REDIS_PORT` are unset; REST must never load it. Do not "unify" the three sites onto one import. The caller already hands `appendBackupRow` a stripped snapshot, so the re-encode is the same primitive minus the metadata deletes it does not need.
  - **The fix is forward-only.** Rows written before it keep their ghosts. `scripts/backfill-strip-ghosts.ts` erases them — dry-run by default, `--apply` writes, `md5(data)`-guarded, each written row re-read and compared. It has run against the local database only; production rows still carry theirs. Filter on erasure, never on size: two carriers re-encode byte-neutral or slightly larger.

- **`rehostMediaUrls` (`src/lib/rehostMediaUrls.ts`) is a fourth site that re-encodes a snapshot through a `Y.Doc`, and it is not a unification candidate either.** It runs only in `duplicateDocument`, on the source's persisted head, before the copy has any row: decode, repoint every `/hypermultimedia/<id>/<file>` URL onto the copy's own prefix, report the objects it saw, re-encode. The direction is the safe one — it re-encodes the OLDER head and nothing has been merged onto it yet. Verified on a real 77,433 B row: a later raw update (one block deleted, one appended) merged onto the re-encoded head kept the later edit, held the block count at 313, and produced visible state identical to the un-rehosted live doc modulo the URL swap. It shares no primitive with the three append sites above — they merge raw then strip, this one rewrites content the merge has not seen — so folding them together buys nothing and re-creates the Redis-at-import problem.
  - **The URL names the prefix to copy from, not the source id, and the scan runs before the copy.** A live production row (`Zrl8S6a5609d4ViFEf5`) already carries its only media URL under a different document (`AwY06BK4pv671bffa6a`), so copying "the source's prefix" copies the wrong objects and leaves the copy pointing at a third document. Bounding the copy by what the snapshot names also stops a deleted media node's orphaned object from being resurrected under a new public URL, and bounds N by what is live rather than by everything ever uploaded. The decode is gated on a raw-byte search for `/hypermultimedia/`: Yjs v1 writes attribute strings as literal UTF-8, so a snapshot without those bytes cannot name media.
  - **The duplicate's media re-host is forward-only.** Copies made before it still share their source's objects, so purging one of those sources still strips its copies. No backfill exists and none is planned; the decision is to fix the path and leave those rows. `scripts/e2e-duplicate-media.ts` pins the contract against real Postgres, the real Supabase purge RPC and real local storage.
  - **The dead-letter drain is a producer, not an append site.** `drainStoreDeadLetterQueue` (`src/lib/queue.ts`, driven by `scripts/drain-store-dlq.ts`) re-enqueues a stranded payload through `enqueueStoreDocument`, so the worker's `FOR UPDATE` merge stays the only code that writes the row. **Never "simplify" it into a direct insert.** The DLQ embeds the raw pre-strip state, so an insert would both replace a newer head with an older snapshot and store the ghosts the merge path exists to drop. Two consequences stay with the operator, and the script prints both. A row written after the entry failed usually already carries the stranded edits, so the replay mints a duplicate version — and a duplicate carrying a `commitMessage` is exempt from `pruneAutosaveVersions` forever. An entry whose document has no rows left replays into `isFirstCreation`, which recreates the metadata row and fires `sendNewDocumentNotification` late. **A soft-deleted document's entry is removed, not parked.** Parking it was the bug: nothing else clears a DLQ entry, so the reaper's later purge made the same entry flip from `skip-trashed` to `replay` on a fixed timer — the drain manufactured the one state it could not handle. For the same reason an entry whose `failedAt` predates `DOC_DELETE_RETENTION_DAYS` is refused outright rather than warned about: past that window a document with no rows is indistinguishable from a first save lost in an outage.

- **Only a purge seals a room; a soft delete closes it but still flushes.** `purgeDocumentFootprint` publishes `{deleted, purged: true}` and `handleDocumentAccessEvent` (`src/lib/accessRealtime.ts`) adds the `Document` to `sealedRooms` only on `purged`, which makes `store()` drop the forced close-time flush. Sealing a soft delete too was a data-loss bug: closing the last connection makes Hocuspocus run `executeNow`, so the drop cost every collaborator up to one debounce window (10 s idle, 60 s max) — and it prevented nothing, because `isFirst` keys on the `Documents` table and a soft delete leaves those rows in place, so `upsertDocumentMetadata` takes its `update: {}` no-op arm. Restore cannot recover the dropped window; it returns the persisted state.
  - **The seal is published after the RPC and the media delete, and before the `deleteMany`.** Earlier and a purge that throws has already closed a room that survives — the client's `deleted` arm calls `stopReconnect()`, so nobody comes back. Later and the close-time flush re-creates the row the purge just removed.
  - **Two windows stay open.** `sealedRooms` is a per-process `WeakSet`, and `publish` resolves on the Redis ack, not on the subscriber having run — a debounce firing inside that gap enqueues before the seal lands. And a job already in `wait` when the seal lands still reaches the worker's first-save branch. Both are as wide as queue latency.

## Retention and schema

- **`trigger` tells a row the server minted from a checkpoint a person chose.** `MACHINE_VERSION_TRIGGERS` (`src/types/queue.types.ts`) is `revert-backup` — the pre-restore safety copy in `versionsStore.ts` — and `schema-migration` — the one-time rebuild in `hocuspocus.config.ts`. The reaper's candidate predicate is `commitMessage IS NULL OR = '' OR trigger IN (…machine…)` (`src/hocuspocus.worker.ts`), so a machine-named row older than `DOC_AUTOSAVE_RETENTION_DAYS` is thinnable and a very old restore stops being undoable. That is the accepted trade: before it, every restore minted two rows that no sweep could ever reach, which was the only genuinely unbounded storage path in the system. A name a person typed stays exempt forever — `checkpoint`, `api`, and `revert` (the `Restored version N` row) are not machine triggers. Rows written before the column keep `trigger = null` and stay exempt.
  - **Never add a server-minted version row without a machine trigger**, and never widen the predicate by matching `commitMessage` text. The trigger column exists to remove exactly that fragility.

- **`@@index([documentId])` must stay. `@@index([documentId, version])` was the duplicate.** In that order, because two independent reviewers got it backwards and dropped the wrong one. `@@index([documentId])` is the narrowest documentId-leading cover for the version-list `count()` — dropping it degrades that count from 8 buffers / 0.168 ms to 20 buffers / 0.332 ms — and it is the presorted key the reaper's Incremental Sort needs. `@@index([documentId, version])` was byte-identical to the index behind `@@unique([documentId, version])`: same columns, same order, same btree. It covered no read and cost a write on every save inside the `FOR UPDATE` transaction; dropping it took the reaper DELETE from 10.4 to 5.8 ms. Removed by `prisma/migrations/20260727090000_drop_duplicate_document_version_index`.
  - Do not justify the drop with `idx_scan=0`. The planner picks arbitrarily between identical indexes and a scratch replica chose the opposite one. The justification is that the two declarations were identical.
  - Keep that migration at exactly one statement. `DROP INDEX CONCURRENTLY` cannot run inside a transaction block, and Prisma's runner wraps a multi-statement file in one.

## Runtime limits

- **The REST server sets `idleTimeout: 60` explicitly** (`src/index.ts`). Bun's default is 10 s and it closes the socket while the handler runs on to completion, so a request that takes longer reports failure over work that succeeded. Reproduced on Bun 1.3.14: the client failed at ~12 s with `request timed out after 10 seconds` and the duplicate still landed, and `useDuplicateDocument.ts` has no dedupe, so a retry stacks a second full copy. The handler that reaches it is `duplicateDocument`, which copies every object its snapshot names, sequentially, inside the request. Bun caps this option at 255 s, so it is a ceiling, not a fix for an unbounded handler — a document whose media cannot be copied in 60 s still fails, and the answer there is to move the copy off the request, not to raise the number.

- **The stateless default arm has a 64 KiB byte budget** (`MAX_STATELESS_RELAY_BYTES`, `src/hocuspocus.server.ts`). The arm re-stringifies the payload and mints one `OutgoingMessage` per connection, with no `readOnly` check and no throttle — `onAuthenticate` continues on a missing token and any public room is joinable with no credentials, so the sender is anonymous. Measured on a real 1024 M cgroup: one ~15 MiB frame to a 60-viewer room → OOMKilled, exit 137; a burst of 30 × 8 MiB to a 30-viewer room → exit 137. The amplifier is room size × burst rate, not frame size; the same burst under the budget peaked at 138 MB with no kill. Anything relayed through this arm that exceeds the budget is dropped with a warn, which is the point.
  - **`server.webSocketServer.options.maxPayload` is not the answer.** Bun ignores the `ws` option and caps frames at its own ~16 MiB, so setting it does nothing.
  - **The arm cannot be deleted.** The webapp sends `{ type: 'docTitle' }` from `DocTitle.tsx` and `MobilePadTitle.tsx`; no named branch handles it, so it falls through to the relay. Deleting the arm breaks live document-title sync between collaborators. A `docTitle` payload is a title string, so 64 KiB is orders of magnitude of headroom.
  - **The arm relays `type: 'docTitle'` and nothing else, and refuses any payload carrying `msg`** (`RELAYABLE_STATELESS_TYPES`, `src/hocuspocus.server.ts`). The relay is unauthenticated and fleet-wide, so a client-chosen envelope was a client-chosen server event: `{type:'private'}` drove every viewer in the room through the webapp's `applyAccessStateless` → `exitSealedDocument` redirect, and `{msg:'document:saved'}` flipped every viewer's status to "Saved" while their edits were still unpersisted. **An allowlist on `type` alone is not enough** — `useYdocAndProvider.ts` reads `msg` before `type`, so `{type:'docTitle', msg:'document:saved'}` passes a type-only guard. The named branches above own every legitimate `msg`. The guard runs ahead of the byte budget so an oversized forgery counts as `type-not-allowed` and not as an OOM probe, and it logs `String(type).slice(0, 64)` because the raw value is attacker-controlled and this file exists to stop an amplifier. No server event is affected: `readOnly`, `private`, `deleted` and `document:saved` all leave through `document.broadcastStateless` and never enter `onStateless`.
  - **`MessageType.BroadcastStateless` (6) is refused in `beforeHandleMessage`.** `MessageReceiver.apply` relays a type-6 frame to every room connection inline, so it never enters `onStateless` and the allowlist cannot see it. That path reaches only the local replica — it does not call `document.broadcastStateless`, so `beforeBroadcastStateless` never fires and `@hocuspocus/extension-redis` never publishes; the `onStateless` relay above does both and is therefore fleet-wide. The refusal drops that document connection with a CLOSE frame, not the socket. That is acceptable only because `@hocuspocus/provider`'s `MessageType` enum has no 6, so no shipped client can reach the close path — **if a future provider version adds one, change this arm before bumping.** extension-redis builds its inbound `MessageReceiver` with no `Connection`, so cross-replica `docTitle` sync never touches this hook.
  - **Both guards are pinned by `scripts/e2e-versions.ts` section `[8]`**, which keys every check on the `stateless_relay_dropped_total{reason}` delta. An absent broadcast alone also passes on a misencoded frame or a wrong room name, so the counter is the only thing that proves the guard fired. `RedisExtension` is gated on `env === 'production'` (`src/config/hocuspocus.config.ts`), so that section proves the local room only; the fleet-wide reach of the relay arm comes from reading the library, not from the test.

- **`refreshPendingStateKeyTtls` derives the state key from the job id and `LRANGE`s the wait list** (`src/lib/queue.ts`). `enqueueStoreDocument` sets `stateKey = STATE_KEY_PREFIX + jobId` and passes the same value as `jobId`, so the key never needs the job hash. **Do not "improve" it back to `getJobs`.** Hydrating every job to read a derivable key cost +428 MB RSS at a 50,000 backlog, inside the same 1024 M WS replicas that hold every loaded room, and `Bun.gc(true)` does not return it. Measured after: 11 ms / +21 MB against 318 ms / +330 MB.
  - **Paging `getJobs` with positive indices is worse than not paging.** BullMQ LPUSHes, so index 0 is the newest job with the freshest TTL and the tail is the oldest. A 20,000 budget over a 50,000 backlog re-armed the newest to 3600 s and left the oldest at ttl=100 s — precisely the loss this function exists to prevent. Deriving the key needs no cursor, so it cannot drift.
  - **Both `wait` and `paused` are read** because `Queue.pause()` RENAMEs one list to the other, so the backlog answers to either name and only one exists at a time.
  - **EXPIREs go out in 1000-key chunks.** ioredis buffers every queued command until `exec()`; one flat pipeline over 50,000 keys held +164 MB on its own.
  - Coverage is the `wait`/`paused` backlog — the worker-outage case this exists for. `delayed`, `active`, and `failed` jobs are no longer re-armed; those lists are bounded (retry ladder, worker concurrency, `removeOnFail` 200 / 7 days), but a job parked in one of them past the 1 h claim-check TTL loses its payload.

## Documented hazards we accept

- **A cross-replica `replace` can delete text the executing replica never saw.** `@hocuspocus/extension-redis` publishes document state from `afterLoadDocument` and `onChange` only — no timer, no anti-entropy — so convergence is edit-triggered. If the handshake for the last edit before a quiet period is lost (measured 21 delivered / 9 lost over 30 server-side kills), the replicas stay divergent after Redis recovers, and the restore's `applyContentToDoc(doc, scratch, 'replace')` deletes only the blocks its own replica holds. Both replicas then converge on the wrong document. The window is bounded, not permanent: Hocuspocus defaults to `unloadImmediately: true` and the config does not override it, so a room unloads as soon as its last connection closes and this needs a client continuously holding the stale replica. The pre-restore backup row is not compromised — `appendBackupRow` merges against the `FOR UPDATE`-locked DB head, so everything already persisted stays recoverable, stale only by the live debounce window. **We deliberately do not build for this.** Restore is reachable two ways, both landing on the same `applyContentToDoc`: the service-role REST route, and the `history.revert` stateless op, which any authenticated writable connection can send — including the anonymous Supabase session every visitor gets. No shipped client sends it, so today's exposure is a hand-crafted frame on top of the conjunction above. Revisit when the history UI starts sending `history.revert`: that turns a coin-flip corruption into a button. Room affinity via a Redis key is not the fix: divergence requires both replicas hosting the room, so `afterLoadDocument` fires on both and the key names an arbitrary one, possibly the stale one.

- **A checkpoint can put its name on bytes the room has already moved past.** `HOCUSPOCUS_INTERNAL_URL` is a service name (`http://hocuspocus-server:4003`) and `docker-compose.prod.yml` runs that service at `replicas: 2`, so the REST→WS hop lands on an arbitrary replica: `internalHop` (`src/lib/internalHop.ts`) and both hop clients have no affinity, no retry and no room probe, and Bun's `fetch` pools keep-alive sockets, so the replica is arbitrary once, then sticky. On a replica that is not hosting the room, `openDirectConnection` loads the persisted head, and `@hocuspocus/extension-redis`'s `afterLoadDocument` resolves without awaiting a peer's state — it resolves inside the `sub.subscribe` callback, right after an un-awaited `publishFirstSyncStep`. That is an internal of extension-redis 3.4.4 — re-read `afterLoadDocument` before bumping it, because the whole hazard derives from it. Two of the three arms are covered: the content apply accepts this in `API.md` (the `PATCH` concurrency note), and the restore is the bullet above, which additionally commits `appendBackupRow` between the open and the commit — a DB round trip the other arms do not have. The checkpoint is what is new. Its commit is an empty `transact`, and `consumeVersionStamp` clears the stamp in `commit`'s `finally` (`src/modules/document-versions/infra/versionOps.ts`), before the disconnect flush. So the checkpoint's NAMED, retention-exempt row can be minted from pre-sync bytes, while the room's converged bytes land on a second row that is unnamed and therefore thinnable — `buildStoreJobId` fingerprints the state, so different bytes mint a different row. **It is latent, and it stays latent.** Both version write routes are `requireServiceRole` and no shipped client calls them — the history sidebar restores client-side through `setContent` (`useVersionRestore.ts` in the webapp). Unlike `history.revert`, a checkpoint has no stateless op: `checkpointOp` is reachable only from `document-versions`' HTTP controller. Revisit when the history UI ships a checkpoint action. **The obvious fix was tried and rejected; do not re-propose it.** Keeping the stamp alive across the disconnect flush does not correct the first row. It mints a second row carrying the same checkpoint name over different content — on every checkpoint, not sometimes — and it re-opens the retention hole the `trigger` column closed above: that row would be named with `trigger = 'checkpoint'`, which no sweep can ever reach. The queue-down direct-write path (`src/config/hocuspocus.config.ts`) writes each flush straight to Postgres with no job id and no dedupe, so with the queue down every checkpoint would leave two permanently exempt rows. A convergence barrier is not the fix either: there is no signal to await, `afterLoadDocument` resolves before any peer replies, and on a cold document no peer exists at all, so a wait would be an unmeasured sleep that shifts a probability.
