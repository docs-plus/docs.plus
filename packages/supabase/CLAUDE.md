# CLAUDE.md — `@docs.plus/supabase_back`

Supabase architecture and safety policy: generated files, migrations vs scripts, seed order, RLS, storage, and quotas. SQL authoring style stays in `.cursor/rules/supabase.mdc`.

Moved verbatim out of the repo-root [AGENTS.md](../../AGENTS.md) so it loads only when working here. Root-level rules (git policy, package manager, code quality, test policy) still live there and still apply.

## Supabase

- **`workspaces.slug` and `workspaces.name` hold `lower(documentId)`, not a slug — they always have.** `join_workspace()` is the de-facto sole writer and inserts `lower(_workspace_id)`. Because `workspaceId === documentId`, the column is a lowercased copy of the primary key under a name that lies. `document_views.document_slug` is the same. **Every lookup against these columns must pass `lower(documentId)`, never `DocumentMetadata.slug`.** Passing the human slug matched nothing. It left the member roster silently empty in every environment. Callers were fixed 2026-07-27. The column itself is deliberately not re-keyed. It is `not null unique` with a regex check, so it cannot be repaired in place. There is also **no deploy pipeline for Supabase SQL** — it goes up by hand, days apart from code. Also do not read `workspaces.created_by` as ownership: it holds the first signed-in _visitor_. `DocumentMetadata.ownerId` owns that fact.
- **`increment_unread_count_on_new_message` auto-enrols on PUBLIC channels only** (guarded 2026-08-03). It enrols every workspace member into `channel_members`, so unread badges cover headings nobody joined. But `internal.can_read_channel` grants read on an active `channel_members` row. Enrolling on a `DIRECT`/`GROUP`/`BROADCAST`/`ARCHIVE` channel would therefore publish it to the whole workspace. Keep the `channel_type_var = 'PUBLIC'` gate on the INSERT; the increment UPDATE stays ungated because it only touches rows that already exist. The `PRIVATE` type itself was dropped 2026-07-27. Dropping an enum value needs the recreate dance: nine policies depend on `channel_type`, two of them on `storage.objects`, and that one blocks `ALTER COLUMN TYPE`.

- **Never edit `packages/supabase/seed.sql`.** Agents and routine changes must not modify it; use `packages/supabase/migrations/` and `packages/supabase/scripts/` only.
- **Never edit `apps/webapp/src/types/supabase.ts`.** It is generated by the Supabase CLI via `packages/supabase` script `types` (`bunx supabase gen types typescript --local` → that path).
- **Webapp types convention.** `apps/webapp/src/types/supabase.ts` is the generated source of truth. The rest of `apps/webapp/src/types/*.ts` (`api.ts`, `domain.ts`, `history.ts`, `message.ts`, `stores.ts`, `tiptap.ts`, `toc.ts`) is where derived/expanded types are authored and re-exported. Build new shared types there and import them — do not redeclare row/payload aliases inline in hooks, components, or stores. SDK types (`@supabase/supabase-js` — `PostgrestError`, `PostgrestResponse`, `AuthError`) come from the SDK directly and bypass this folder.
- **After any SQL change, regenerating types is required, not optional.** Any work that touches `packages/supabase/migrations/**` or `packages/supabase/scripts/**` ends with running `bun run --filter @docs.plus/supabase_back types` from the repo root (local Supabase + root `.env.local`). The same change must include the regenerated `apps/webapp/src/types/supabase.ts`. The agent runs this command itself; never hand-edit the generated file.
- SQL authoring style lives in `.cursor/rules/supabase.mdc`; keep this section focused on project architecture and safety policy.

- Browser code imports the `supabaseClient` singleton.
- Apply a single migration locally without resetting (preserves shared local state across worktrees) with `docker exec -i supabase_db_docsplus_supabase psql -U postgres -d postgres < packages/supabase/migrations/<file>.sql`. `bunx supabase db reset` wipes everyone else's state; `supabase db query -f` does not handle multi-statement files (`SQLSTATE 42601: cannot insert multiple commands into a prepared statement`).
- **Editing an uncommitted migration file requires re-apply.** When iterating on an unmerged migration, the file on disk diverges silently from what's running in `supabase_db_docsplus_supabase` until you re-apply. The same holds for behaviour-only changes to its paired `scripts/*.sql`. Symptoms of forgetting: FE realtime channels that subscribe with `{ config: { private: true } }` thrash retries, because the server lacks the matching `realtime.messages` policy. FE features that call new RPCs / new return columns also silently see the old behaviour. Re-apply via the `docker exec -i ... psql ... < migrations/...sql` form above (idempotent `drop policy if exists` / `create or replace function` make re-runs safe). If only the script changed, prefer `docker exec ... < scripts/<file>.sql` so a later `db reset` reproduces the same state.
- **Migrations and `scripts/*` are paired.** Every change applied via a migration must be mirrored in the corresponding source-of-truth `scripts/*.sql` file. That keeps `db reset` reproducing the production state; it seeds from `seed.sql`, which `generate-seed.ts` generates from `scripts/*.sql`. Do not land migration-only or scripts-only changes for the same invariant. The workspace `reset` script regenerates `seed.sql` before resetting; a `scripts/*.sql` edit without a regenerated `seed.sql` leaves fresh clones seeding stale schema.
- **Seed order is load-bearing.** `generate-seed.ts` concatenates `scripts/` by numeric prefix. A script may therefore only call SQL objects defined in an earlier-numbered file. SQL-language function bodies resolve at CREATE time, and a forward reference aborts the whole fresh-volume seed. The `internal.*` policy primitives (`is_workspace_member`, `is_channel_member`, `can_read_channel`) therefore live in `10-0-func-helpers.sql`, not `13-RLS.sql` (which keeps their grants, hardening, and policies) — do not move them back. Verify any new cross-file SQL dependency against a fresh `supabase start` on empty volumes.
- **Remote `db push` vs local reset.** `[db.migrations] enabled` in `packages/supabase/config.toml` stays `false` for day-to-day local dev (`db reset` seeds from `scripts/00-bootstrap.sql` + the generated `seed.sql`, per `[db.seed].sql_paths`). Toggle `true` only while pushing to remote, then set it back to `false` (never commit it `true`). Never delete a migration file that remote has already applied — use `supabase migration repair --status reverted <version>` if consolidating history. Bulk function catch-up for prod gaps: edit `scripts/`, run `bun run --filter @docs.plus/supabase_back generate:functions-parity-migration` (writes a timestamped migration from an allowlisted script subset; adds `DROP TRIGGER IF EXISTS` before bare `CREATE TRIGGER`). One-shot data backfills stay hand-written migrations, not in `scripts/`.
- **`db push` history divergence — repair vs push.** The remote `supabase_migrations.schema_migrations` table drifts from local `migrations/`, because prod gets objects via `scripts/*` + parity migrations without a history row. So `db push` refusing with "remote versions not found" / "does not match local files" is normal, not corruption. Ground truth is `bunx supabase migration list` (Local | Remote columns; empty `remote` = not applied) — run it BEFORE any repair. `supabase migration repair --status applied <v>` only edits the history table, it does NOT run the SQL: mark-applied ONLY versions whose objects are already live on prod (the pre-last-deploy prefix). A genuinely-new migration (empty `remote`) must be **pushed**, never repaired-applied — marking it applied makes `db push` skip it forever so its objects silently never get created. Phantom remote-only versions come from out-of-band pushes. They are in remote history but never in git — check `git log --all -- migrations/<v>_*`. `repair --status reverted <v>` removes the bogus row, and its schema changes become untracked drift. All repo migrations are idempotent, so a clean push over partially-present objects is safe; an "already exists" error means non-idempotent SQL applied out-of-band. Do NOT blindly follow the CLI's blanket "mark applied" suggestions.
- **Migrations must ship dependencies they call.** If a migration `create or replace`s a function that calls `internal.*` helpers, those helpers must appear in the same migration or an earlier one. They must not live only in `scripts/`, because prod never runs `db reset`. Trigger functions that write other users' `channel_members` rows must end with `SECURITY DEFINER`, in both `scripts/` and the migration path. Otherwise RLS column grants block inserts after `13-RLS.sql`.
- **Explicit table GRANTs for `authenticated` (and `service_role`) are required — do not rely on Supabase default privileges.** Newer local Supabase images no longer auto-`GRANT ALL` on `public` tables to those roles. RLS alone is not enough: chat RPCs like `fetch_message_window` / `get_channel_aggregate_data` are `SECURITY INVOKER`. A missing GRANT therefore surfaces as Postgres `42501` → PostgREST **403** for signed-in users, while anon still works (`29-lint-hardening.sql` re-grants SELECT only for `anon`). Canonical grants live in `scripts/13-RLS.sql` (mirrored by migration `20260716130500_grant_authenticated_chat_table_privileges.sql`); after a reset, if authed chat bootstrap 403s with `permission denied for table messages|channels|channel_members`, check `authenticated` table privileges first.
- **The seed batch runs with an empty `search_path` and as the `postgres` role, and both bite.** Verified 2026-09-04, one statement at a time. An extension that names no schema of its own fails: `pg_cron` and `pgmq` name theirs, `pg_net` is relocatable and does not, so a bare `create extension pg_net` raises `3F000: no schema has been selected to create in` and kills the whole reset on `00-bootstrap.sql`. Give any such extension `with schema extensions`, where `pgcrypto`, `pgjwt` and `uuid-ossp` already live. Separately, `realtime.messages` is owned by `supabase_realtime_admin`; `postgres` is not a member of that role and cannot become one, because `supabase_admin` is the only superuser. Measured on that table: `CREATE POLICY` and `DROP POLICY` **both succeed**, and only `ALTER TABLE` and `COMMENT ON POLICY` raise `42501`. **Never add a `COMMENT ON POLICY` on `realtime.messages`** — put the text in a `--` line comment, as `07-3-notification-broadcast.sql` and `10-functions.sql` now do. An `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` there must be guarded on `relrowsecurity`; current images already ship it enabled.
- **`COMMENT ON ENUM LABEL` is not valid Postgres.** It raises `syntax error at or near "ENUM"`. The commented block in `01-enum.sql` therefore can never be uncommented, and every label meaning in that file is dead text. Do not add to it expecting it to run.
- **A new `notification_category` value enrols in every type-blind consumer, and there are two.** `enqueue_push_notification` (`07-4`) gates `mention`, `reply` and `reaction` with **no `else`**, so an ungated type pushes with no per-type preference check. `queue_email_notification` (`07-5`) ends its `case` with `else should_queue := true`, so an ungated type mails by default. Name the new value in both, or one channel gets an accidental default. **Both live in `scripts/` only, so a gate must also be recreated inside the migration** — remote never runs `db reset`.
- **A `workspaces` row implies a `channels` row, so a read path may guard on the channel and must never create one.** `join_workspace` is the only writer of `public.workspaces`, and it always follows that insert with a `workspace_members` insert, whose `notify_user_join_workspace` trigger mints the channel. `notify_document_content_change` shipped with a `public.channels` insert that was dead on the normal path, cascaded into `channel_creator_as_admin` and `increment_member_count`, and raced two concurrent callers into `23505`, which aborts the whole RPC.
- **`idx_notifications_content_change_open` is load-bearing, not decoration.** The 24-hour dedupe `not exists` in the fan-out is not evaluated per row: the planner de-correlates it into a plain Join Filter. Measured on a 600k-row table at 10,000 followers, a second call inside the window took 2081 ms with `Rows Removed by Join Filter: 49,995,000`; with the index it is a Hash Anti Join at 4.9 ms. It is partial (`where type = 'content_change' and readed_at is null`), so it holds 592 kB, and the first-call insert measured 855.8 ms without it and 833.8 ms with it. Reading the index list suggests `idx_notifications_receiver_readed` covers this. It does not — that index cannot serve an inner side reached by a Join Filter.
- **A `SECURITY DEFINER` function that browser code calls must be listed in `29-lint-hardening.sql` §6 — its own `grant execute` is not enough.** That file's §5 loops over every `prosecdef` function in `public` owned by the migration role, and revokes EXECUTE from `public, anon, authenticated`. Its §6 re-grants only the hardcoded `user_facing_names` array. Seed order is numeric, so §5 silently undoes any grant a lower-numbered script made. `get_document_member_previews` and `get_document_members` granted themselves at `10-8-func-workspace_members.sql:207-208` and still answered `42501 permission denied` to fully signed-in users after every `db reset`, because neither name was in the array. Diagnose with `has_function_privilege('authenticated', p.oid, 'EXECUTE')` against `pg_proc`, and compare with a whitelisted function such as `join_workspace`. The sweep is local-seed only, and no migration carries it. So the fault appears at `localhost:54321` and never in production, which makes it read like a client-side auth bug.
- **`supabaseClient.rpc(...)` is lazy.** It returns a `PostgrestBuilder`; the request only leaves the browser when `.then(...)` / `await` / `.single()` / `.maybeSingle()` is attached. Fire-and-forget calls that drop the result (e.g. a debounced cursor advance) MUST attach `.then((res) => { if (res.error) console.warn(...) })`, or the network call silently never dispatches. Any `supabaseClient.rpc(` without a continuation is a bug.
- **Storage RLS is path-based, not column-based.** Bucket policies for `user_avatars` / `channel_avatars` check `(storage.foldername(name))[1] = (select auth.uid()::text)`, NOT `owner` (uuid) or `owner_id` (text). Storage-api v1.54.1 doesn't reliably auto-populate either column on insert; predicates against them evaluate `NULL = …` → false → 403 "new row violates RLS policy". The FE writes paths as `{userId}/{filename}` (`useAvatarUpload` uses `${user.id}/avatar.png`; `Config.app.profile.getAvatarURL` emits the matching read URL). Encoding ownership in the path is Supabase's canonical pattern and matches Slack/Discord/Linear conventions.
- **Storage bucket policies are CRUD-complete, not write-only.** Migrations that re-declare INSERT / UPDATE / DELETE policies on `storage.objects` MUST also confirm a matching SELECT policy exists. Supabase Storage runs `INSERT … RETURNING` (or INSERT followed by SELECT) on every upload. A missing SELECT policy then returns the same generic "new row violates row-level security policy" 403, which misleadingly points at the INSERT. The actual denial is on the readback. `scripts/12-buckets.sql` declares SELECT policies for `user_avatars` / `channel_avatars` / `media`. Each is scoped by `bucket_id` plus the same path/owner predicate as its write policies. The migration tree must keep parity. Public-URL reads (`/storage/v1/object/public/...`) take a different code path that doesn't go through PostgREST RLS. The avatar display can therefore work while uploads silently 403. That is exactly how this gap survived three rounds of "fix the RLS" migrations.
- **`storage.objects` EXISTS subqueries:** inside `exists (select 1 from public.channels c where …)`, unqualified `name` binds to **`c.name`** (channel slug), not the storage row — correlate media paths with **`objects.name`** (e.g. `(storage.foldername(objects.name))[2]` for `{userId}/{channelId}/…`). Bare `foldername(name)` in public-channel chat media SELECT policies broke anon and non-member signed-URL reads; channel members still worked via the member policy.
- **Avatar source-of-truth is a two-field hybrid.** `users.avatar_url` holds the OAuth provider URL (set by `handle_new_user` from Google's `picture` claim on signup); `users.avatar_updated_at` is the "user has uploaded a custom avatar" indicator. `<Avatar>` reads `avatar_updated_at` first — if set, derives the bucket URL `${BUCKET}/${id}/avatar.png?${avatar_updated_at}` (the timestamp doubles as cache-buster); if null, falls back to `src` (= `avatar_url` = OAuth URL). `useAvatarUpload.handleUpload` overwrites `avatar_url` with the bucket URL. After a custom upload, `avatar_url` is the bucket URL, not the OAuth one. `handleRemove` nulls BOTH `avatar_url` and `avatar_updated_at`. It writes DB-first, before deleting the storage object, so a render never points at a deleted file. Removing a custom avatar therefore drops to the default avatar; it does not restore the OAuth picture.
- **`user_avatars` rejects AVIF.** Bucket allowlist in `scripts/12-buckets.sql` is jpeg/png/gif/webp/svg only; the file picker’s `image/*` still admits AVIF on macOS. Always run `prepareAvatarFile` (`settings/utils/`) before upload, so unsupported/oversized images become bucket-safe PNG/WebP/JPEG. Do not widen the bucket MIME list, and do not merge this helper into chat-media downscale.
- **Channel/workspace IDs are `varchar(36)`, not `uuid`.** `channels.id`, `channels.workspace_id`, and `workspaces.id` are declared `varchar(36) default uuid_generate_v4()` (`scripts/04-channels.sql:5-6`) — they hold UUID-shaped text in a `varchar` column, and `messages.channel_id` follows the same typing via its FK. SQL that compares them against a real `uuid` (e.g. `auth.uid()`, a `uuid`-typed column, or a `::uuid` literal) must cast both sides to the same type or Postgres throws `operator does not exist: character varying = uuid`. This bit the chat-media storage RLS / `validate_message_medias` path, where the `media` object path segment (text) is compared to `channel_id`. Keep those comparisons text-vs-text (or cast explicitly), never `varchar = uuid`.
- **RLS predicates initplan-wrap auth calls** (Supabase lint 0003): write `(select auth.uid())`, never bare `auth.uid()`. For row-independent helper calls, wrap the whole call — `(select public.is_admin((select auth.uid())))`. The linter also flags a bare `auth.<fn>()` nested inside helper-call arguments. The 2026-07-17 sweep cleared all 21; keep new policies clean.
- **`notifications` has no authenticated INSERT policy — mention/system trigger functions must stay `SECURITY DEFINER`** (`scripts/13-RLS.sql` §2i). Recreating trigger bodies without re-applying `SECURITY DEFINER` breaks @mention sends with Postgres `42501` on the `notifications` INSERT. This is distinct from the `channel_members` rule above — different trigger family, same failure class.
- **Any SQL that `DELETE`s from `storage.objects` must first `perform set_config('storage.allow_delete_query', 'true', true)`.** That covers the soft-delete GC `internal.delete_chat_media_paths` + `internal.cleanup_orphan_chat_media`. Supabase's `storage.protect_delete` trigger otherwise raises `Direct deletion from storage tables is not allowed` (errcode 42501). The error bubbles up and fails the whole message soft-delete UPDATE. The flag is the same one the Storage API sets; `is_local = true` scopes it to the GC transaction.
- **Chat-media quota:** 10 GB/workspace is enforced by `internal.enforce_media_workspace_quota`. That is a `BEFORE INSERT` trigger on `storage.objects` for `bucket_id = 'media'`. Quota bytes come from `internal.media_workspace_quota_bytes()` only — stats RPCs, the trigger, and admin UI read that helper (no TS quota constant). Path aggregation is centralized in `internal.media_workspace_usage_rows()` (`split_part(path, '/', 2) = channel_id`; upload paths in `uploadChatMedia.ts`).
- **`get_workspace_media_storage_stats` / `get_all_workspace_media_storage_stats` / `get_workspace_media_storage_summary`** (`10-4-func-chat-media-features.sql`) use `workspace_id varchar(36)` with text equality — never cast channel/workspace IDs to `uuid` (see the varchar(36) rule above). Per-workspace and fleet RPC rows share the same shape (`slug`, `name`, `quota_bytes`, `usage_percent`).
- Orphaned pre-send uploads are reclaimed daily by the `cleanup-orphan-chat-media` pg_cron job (`scripts/16-cron-jobs.sql`; the migration schedules it inside a `pg_extension` guard).
- **`document_views` (and its `document_view_stats` / `document_views_daily` rollups) are keyed by `lower(documentId)`, not the human slug.** `enqueue_document_view` stores `lower(trim(<WS room name>))`, and the room name is the 19-char documentId. The `document_slug` column name lies. Any lookup or purge against these tables must match `lower(documentId)`. `purge_document_footprint` deletes on `lower(p_document_id)`, with `lower(p_slug)` kept as belt-and-braces. This was fixed 2026-07-15 — the previous slug-only match deleted zero rows and left purged docs' analytics behind.
